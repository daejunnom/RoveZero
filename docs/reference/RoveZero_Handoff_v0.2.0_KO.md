# RoveZero
## GPU 중심 체스 엔진 연구·평가 핸드오프

**버전:** 0.2.0 / **기준일:** 2026-10-02 / **상태:** 사용자 검토용 설계 초안

**프로젝트명:** RoveZero (로브제로)  
**GitHub 저장소명:** `rovezero`  
**영문 설명:** A research chess engine for reusable computation and adaptive inference.

> 매 포지션을 처음부터 해석하는 대신, 이미 계산한 내용을 재사용하고 필요한 곳에만 추가 계산을 쓰는 표준 체스 엔진.

**이름의 의도:** Rove의 탐색 이미지를 사용하되 기존 엔진 이름을 직접 이어 붙이지 않는다. 공통 접미사 Zero는 유지한다. 구 문서명은 PlyZero이며, RoveZero는 사용자 승인 전 제안이다.

이 문서는 기존 대화의 첫 아키텍처·학습 제안과 이후의 LLM·영상·데이터 처리·렌더링·수치해석 아이디어를 통합한다. 알고리즘의 출처와 체스 적용 가설을 분리하여, 채택·보류와 기각 사유를 기록할 수 있게 구성했다. 기각한 카드도 보존한다. 코드 구현, 학습, 벤치마크, Elo 대국은 아직 수행하지 않았다.

`Zero`는 이름의 일부다. 교사 엔진 증류와 기존 가중치 재사용을 허용하므로, 무지식·무인간데이터·자기대국만의 학습을 의미하지 않는다. 저장소 생성·이름 확보·상표 권리 확인은 이번 산출물에 포함되지 않는다.

## 읽는 순서

| 검토 목적 | 먼저 볼 부분 |
|---|---|
| 목표와 확정 사항 | 1장 |
| LC0와 공정하게 비교하는 방법 | 2장 |
| 핵심 엔진 구조와 역할 경계 | 3~4장 |
| 기존 알고리즘 46개와 출처 | 5~9장 |
| 학습·실행·대국 실험 순서 | 10~12장 |
| 기존 결정 이력·개정 결정표 | 13장, 17.4절 |
| CPU/GPU 판단 기준과 신흥 엔진 조사 | 14~15장 |
| 추가 알고리즘·갱신 실험 순서 | 16~17장 |
| 출처 원문과 적용 한계 | 18장 |

**표기 규칙.** ‘확정’은 사용자 요청에서 정해진 조건, ‘권고’는 이 문서의 초기 기본안, ‘가설’은 실험으로 검증해야 하는 아이디어다. 후보 표기의 ‘우선·후속·보류’는 구현 순서 제안이지 Elo 예측이나 채택 결정이 아니다.

**근거 구분.** ‘체스 근거’는 체스에서의 연구·구현이 존재한다는 뜻이고, 최신 LC0보다 강하다는 뜻은 아니다. ‘타 분야 근거’는 원래 분야에서의 원리·실험이 있다는 뜻이다. 각 카드의 ‘적용’은 별도로 명시하지 않는 한 RoveZero의 연구 가설이다.

**주석 사용법.** 본문의 [R번호]는 18장의 원문 링크와 출처 주석으로 연결된다. 외부 성능 수치는 원래 비교 조건을 벗어나 RoveZero의 예상 속도나 Elo로 환산하지 않는다.

## 0. 이번 개정에서 바뀐 것

**사용자 검토용 v0.2.0.** 원래 46개 후보 A01~E12는 모두 보존했다. 여기에 현대 체스 엔진의 핵심·세부 기법 30개를 F01~F30으로 추가하여 **총 76개 검토 카드**로 확장했다. 일부 F 카드는 기존 아이디어의 구체화·비교 기준이므로, 76개의 독립적인 Elo 이득을 뜻하지 않는다.

**반대 근거 보강:** 2026-09-05 Stockfish 19 공식 발표의 pawn-pair·QAT·작은 보조 네트워크 제거도 함께 반영했다. 이중 평가기의 채택과 제거 모두 특정 모델·탐색 조건에 의존하며, 한 엔진의 변경으로 모든 혼합 구조를 기각하지 않는다. [^R93]

**가장 중요한 수정:** ‘계산을 변경분만 갱신하면 GPU 엔진에도 유리하다’는 일반화를 하지 않는다. 작은 순차 갱신은 CPU에서 유리할 가능성이 높지만, GPU에서는 작은 커널·불규칙 접근·부모 대기·전송 때문에 손해일 수 있다. 모든 카드에 CPU 적합성, GPU 직접 실행 적합성, GPU 중심 시스템에서의 활용성, 권장 배치를 별도로 적었다. 이 평가는 전부 **설계 추론치·미측정**이다.

### 0.1 이름: RoveZero — 독립적인 탐색 엔진 이름

권고 프로젝트명은 **RoveZero(로브제로)**, GitHub 저장소명은 **`rovezero`**다. `Rove`의 탐색 이미지를 담았으며 특정 모델·하드웨어·토크나이저 구조에 이름을 묶지 않는다. Leela·Stockfish 등 기존 엔진 이름을 직접 포함하거나 가까운 표기로 치환하지 않는다. 공통 접미사 `Zero`는 사용자의 앞선 선호에 따라 유지한다. 이름의 유사성으로 계보를 표시하기보다는, 실제 코드를 선택한 뒤 원저작자·기반 commit·변경 범위를 명시한다.

이전 문서의 `PlyZero`와 개정 중 제시했던 `ReelaZero / Reela Chess Zero`는 현재 명명안이 아니다. 후자는 사용자의 추가 요청에 따라 제외했다. 이번 이름은 검토안이며 승인·저장소 생성은 하지 않았다.

사용자가 지정한 Redfish는 공개 토이 엔진과 구분했다. 확인한 **2019년 TCEC16 보고서 PDF 7쪽의 각주 9**는 당시 Redfish를 특정 Stockfish 빌드와 하드웨어 구성으로 설명하고, 본문에서는 해설용 분석 엔진으로 다룬다. 공식 아카이브의 검색 결과에도 LCZero 대 Redfish 보너스 대국 항목이 있다. 이 자료만으로 모든 시기의 Redfish 또는 별도 신규 아키텍처를 단정하지 않는다. 기존 엔진과의 실제 관계는 이름보다 출처·기반·차이로 명확히 기록한다. [^R68] [^R69]

2026-10-02의 GitHub 공개 저장소명 검색 `rovezero in:name`에서 일치 결과를 찾지 못했고, 공개 웹의 정확한 이름 검색에서도 체스 엔진 충돌을 확인하지 못했다. 제한적인 검색 결과이며 이름 확보·전 세계 무중복·상표 권리를 보증하지 않는다. 저장소는 생성하지 않았다.

### 0.2 읽기 전에 구별할 네 가지

| 구분 | 문서의 의미 |
|---|---|
| 구현 사실 | 선택한 공개 소스 또는 공식 문서에서 해당 기법을 확인했다. 최초 발명자·효과의 크기를 입증하지 않는다. |
| 저자 보고 | 해당 엔진의 릴리스·연구 결과다. 다른 기법이 함께 바뀌었을 수 있어 단일 기법의 Elo로 환산하지 않는다. |
| 적합성 추론 | 연산 형태·배치·메모리·의존 관계를 바탕으로 한 가설이다. 모든 높음/조건부/낮음은 미측정이다. |
| 프로젝트 결과 | 이번 개정에는 없다. 구현·학습·프로파일링·대국을 아직 수행하지 않았다. |

원래 1~13장의 설명과 카드 의미는 유지하되, 구현 우선순위가 충돌하면 **14~17장의 GPU 중심 개정 기준**을 우선한다. 낮은 적합성은 삭제 사유가 아니라 배치·실험 조건을 바꾸어 검증할 이유다.

## 1. 목표·범위·결정 상태

### 1.1 목표

최우선 목표는 **LC0와 같은 하드웨어·시간 예산에서 더 높은 대국 득점률을 얻는 것**이다. 중간 목표는 계산 재사용, 유용한 평가 처리량, 메모리 효율, 학습 비용 개선이다. FLOPs·NPS·퍼즐 정확도는 원인 분석 지표이며 최종 대국을 대체하지 않는다.

대상은 표준 체스다. 증강체스의 카드·가변 보드·새 규칙은 초기 범위에서 제외한다. 다만 규칙 엔진과 모델 입력을 분리하여 이후 확장 가능성은 남긴다. 자연어 LLM이 문장을 생성하며 직접 착수하는 구조는 핵심 목표가 아니다. 언어 모델 분야에서 발전한 **저차원 표현·캐시·조건부 계산·증류·실행 최적화의 원리**를 체스에 맞게 다시 설계한다.

### 1.3 기존 연구와의 위치

LC0에는 이미 64칸 토큰 Transformer와 체스 관계를 반영하는 구조가 있다. BT4는 Chessformer 논문의 Leela-CF와 같은 네트워크로 설명되어 있다. 따라서 오래된 CNN만을 상대하여 ‘토크나이저 도입 효과’를 주장하지 않는다. [^R01] [^R02]

증분 accumulator는 NNUE에 이미 있고, LC0의 변경 기록에도 CUDA Graph·fused attention·배치·동시성 최적화가 있다. 새로움은 이런 명칭을 붙이는 데 있지 않고 **더 풍부한 특징을 얼마나 안전하게 재사용하고, 실제 탐색에서 시간을 얼마나 절약하는가**에 둔다. [^R03] [^R63]

설계 목표는 강하지만 결과는 미정이다. +10 Elo, 2배 가속, 특정 GPU에서의 우위 같은 수치를 현재의 성과나 약속으로 기록하지 않는다.

## 2. 대국·시간·Elo 평가 계약

이 장은 구현보다 먼저 잠글 평가 규칙이다. 흑백 교대와 동일 시간 예산은 고정하고, 구체적인 시간·대국 수는 아래 권고안을 검토한 뒤 설정 파일로 확정한다.

### 2.1 흑백 교대의 정확한 의미

한 시작 포지션 P에 대해 **1판: RoveZero 백 / LC0 흑**, **2판: LC0 백 / RoveZero 흑**으로 둔다. 두 판은 같은 보드, 같은 실제 차례, 같은 캐슬링·앙파상·카운터 및 사용 가능한 이력에서 시작한다. 보드를 뒤집거나 기물의 색을 바꾸는 것이 아니라, 그 포지션의 백·흑을 담당하는 엔진만 교환한다.

각 두 판에 같은 `pair_id`와 `opening_id`를 부여한다. 두 판의 실행 순서는 배치마다 균형 있게 바꿔 발열·순서 영향을 줄인다. 같은 PGN 시작 경로를 쓰는 경우 두 엔진에 동일하게 전달한다. FEN만 사용한다면 과거 반복 이력이 없다는 사실과 초기화 규칙을 명시하고, 보이지 않는 과거를 추정하지 않는다.

서로 다른 시작 포지션을 충분히 사용한다. 같은 결정적 엔진·같은 상태·같은 설정을 단순 반복한 결과를 새로운 독립 정보처럼 취급하지 않는다. 시작 포지션 추출 기준과 난수 seed를 대국 전에 고정한다. Fastchess나 Cute Chess 같은 기존 러너를 우선 사용하고, 실제 PGN으로 흑백 교대가 수행되었는지 감사한다. [^R54] [^R55]

### 2.2 ‘동일 연산 시간’의 두 가지 실험

| 트랙 | 시간 배정 | 의미와 용도 |
|---|---|---|
| T1: 주 평가 | 두 엔진에 동일한 기본 대국 시간 + 동일한 수당 증분 | 시간 관리·탐색·캐시·모델을 합친 실제 엔진 강도 |
| T2: 통제 실험 | 같은 포지션·각 착수에 동일한 movetime 예산 | 시간 배분 효과를 줄이고 수당 계산 효율을 비교 |
| T3: 진단 전용 | 동일한 고유 신경망 평가 수 또는 명시한 탐색 예산 | 평가 품질과 실행 속도의 원인 분리. 최종 Elo 판정 대용 아님 |

**T1에서 동일한 것은 ‘허용 시간’이다.** 한쪽이 일찍 착수하면 실제 소비 시간은 다를 수 있다. 정확히 같은 수당 허용 시간이 필요한 비교는 T2로 표시한다. UCI의 시계·증분·movetime 의미를 혼동하지 않는다. [^R56]

권고 시작값은 T1 개발용 **60초+0.6초**, 별도 확인용 **180초+1.8초**다. T2는 **100ms와 1,000ms**를 초기 후보로 둔다. 이 숫자는 문헌의 표준을 주장하는 것이 아니라 프로젝트 설정 제안이며, 실제 장비에서 타임아웃·프로토콜 오버헤드를 먼저 측정하고 최종값을 잠근다.

### 2.3 시간에 포함할 비용과 공정성

신경망 커널 시간만 맞추지 않는다. `go` 이후의 입력 특징 생성, 캐시 조회·복원·재구성, CPU/GPU 전송, 배치 대기, 평가, 탐색 선택·역전파, 결과 출력까지의 **벽시계 시간**을 측정한다. 비동기 GPU 호출의 시작 시간만 재서 완료 시간처럼 보고하지 않는다.

가중치 로딩·모델 컴파일·일반적인 워밍업은 두 엔진에 같은 정책으로 대국 전에 허용하고 별도로 기록한다. 평가 시작 포지션을 미리 분석하는 워밍업은 금지한다. `position` 처리나 상대의 차례를 이용한 숨은 신경망 평가·추측 실행은 허용하지 않는다. UCI 이전 처리의 비용 차이가 의심되면 T2의 추가 계측으로 상태 전달부터 출력까지도 기록한다.

`Ponder`는 양쪽 모두 끈다. 생각 시간 중의 선행 평가·형제 노드 계산은 허용하되 그 시간을 전부 자기 예산에 넣는다. 상대 차례의 배경 탐색, 다른 대국에서 얻은 결과 유입, 온라인 가중치 갱신은 주 평가에서 금지한다. 게임 안에서 자기 시간으로 만든 캐시·트리 재사용은 허용하고, 새 게임 시작 때 게임별 캐시·학습 상태를 초기화한다.

### 2.4 하드웨어·메모리·기준선 고정

같은 CPU/GPU 모델·전력 정책·드라이버·물리 코어 상한·RAM/VRAM 상한을 적용한다. 서로 다른 엔진에서 같은 `Hash` 숫자가 같은 전체 메모리를 뜻한다고 가정하지 않는다. 각 엔진은 같은 자원 한도 안에서 배치·스레드·정밀도를 별도로 튜닝할 수 있지만, 튜닝은 최종 평가 세트 밖에서 수행한다.

단일 GPU에서는 **동시에 한 대국만**, 그리고 생각 중인 엔진만 GPU 계산을 하게 하는 구성을 우선한다. 두 모델이 함께 상주하는 경우 메모리 경쟁·자동 offload가 없는지 확인한다. 함께 들어가지 않으면 비교용 동일 GPU를 각각 제공하고 하드웨어 배정을 교차시키거나, 자원 조건을 다시 정한다. 한쪽 모델의 교체·전송 비용만 임의로 시계 밖에 숨기지 않는다.

기준 LC0는 실행 직전에 바이너리 commit, 네트워크 SHA-256, 검색 알고리즘, 백엔드, 정밀도, 옵션 전체를 기록하여 고정한다. ‘LC0 최신’이라는 이름만 기록하지 않는다. 안정 버전·개발 버전 결과를 혼합하지 않고, 새 기준선을 도입하면 새로운 실험군을 만든다. Transformer 기준선과 호환되는 정상 동작 백엔드를 선택한다. [^R57] [^R63]

### 2.5 득점률과 Elo

RoveZero 관점에서 W=승, D=무, L=패, N=W+D+L로 기록한다. 원시 승률 W/N도 함께 표시할 수 있지만, Elo 환산에 사용하는 것은 **득점률 s=(W+0.5D)/N**이다. 무승부를 제거하지 않는다.

일반적인 logistic Elo 차이는 다음과 같다: **ΔElo = 400 · log10(s / (1 − s))**. 이 값은 고정한 상대·장비·시간·시작 포지션 분포에 대한 상대 차이다. 인간 FIDE나 Lichess 절대 Elo로 변환하지 않는다. s=0 또는 1인 극단 표본에 유한한 점추정치를 꾸며 넣지 않고 경계·불확실성을 보고한다.

흑백 교대 한 쌍의 합계 점수는 0, 0.5, 1, 1.5, 2 중 하나다. 각 빈도 `n0…n4`와 총 쌍 수 M을 보존하며, s=(0·n0+0.5·n1+1·n2+1.5·n3+2·n4)/(2M)로 원시 WDL과 교차 확인한다. 1점에는 2무와 1승1패가 함께 포함되므로 원시 WDL도 삭제하지 않는다.

Fishtest의 pentanomial 접근을 참고해 두 판의 상관을 반영한다. 같은 opening을 여러 번 사용했다면 최종 신뢰구간에서 opening 단위의 추가 군집 상관도 고려한다. **일반 Elo와 Fishtest의 normalized Elo는 다른 척도**이므로 결과·검정 설정에 척도를 명시한다. [^R53]

### 2.6 표본 수·검정·승격

초기 smoke test는 제안상 **100쌍=200판**으로 동작·타임아웃·설정 오류만 확인한다. 작은 Elo 이득의 근거로 사용하지 않는다. 개발 중 후보 비교에는 검증된 pentanomial SPRT/GSPRT 구현을 사용할 수 있다. H0/H1, alpha/beta, Elo 척도, 최대 쌍 수, 중단 조건을 첫 결과를 보기 전에 기록한다. 중간에 경계나 척도를 바꾸지 않는다.

최종 확인은 튜닝에 쓰지 않은 시작 포지션에서 **고정 표본 대국**을 우선 권고한다. 최초 계획 후보는 2,000쌍=4,000판이지만, 이 표본이 모든 +5 Elo 같은 작은 효과를 판별한다는 뜻은 아니다. pilot의 분산과 검출할 최소 효과를 바탕으로 표본 수를 먼저 확정한다. 예산 상한에서 결론이 나지 않으면 ‘불확정’으로 기록하며, 유리한 순간에 고정 표본 실험을 임의 종료하지 않는다.

승격 권고 조건은 사전 정의한 주 T1 조건에서 **상대 ΔElo의 95% 신뢰구간 하한이 0보다 큼**, 규칙·계약 오류 없음, 시간·자원 조건 충족이다. 긴 시간 확인 실험과 다른 seed·장비 재현 결과를 별도 표시한다. 더 빠르지만 대국 이득이 불확실하면 ‘실행 개선 후보’로 남길 수 있고, 승격된 강한 엔진이라고 부르지 않는다.

여러 후보를 같은 세트에서 골랐다면 선택 편향이 있다. 별도 holdout을 재사용해 계속 튜닝하지 않는다. 서로 다른 시간 제어의 결과를 임의로 합쳐 하나의 Elo로 만들지 않는다. 순차 검정이 끝난 표본에 단순 고정 표본 신뢰구간을 붙여 선택 효과를 무시하지 않는다.

### 2.7 판정·실패 처리·필수 기록

엔진 자체의 불법 수·크래시·시간 초과는 사전 규칙에 따라 패배로 포함하고 빈도도 별도로 보고한다. 인프라 장애는 사전 정의한 객관적 조건에서만 무효 처리하며, 해당 pair 전체를 새 실행 ID로 재실행한다. 불리한 게임만 골라 제거하지 않는다.

초기 주 평가는 평가점 기반 조기 승패 판정을 끄는 것을 권고한다. 테이블베이스는 양쪽 접근·경로·probe 설정·판정 정책을 같게 하거나 양쪽 모두 끈다. 수 제한에 걸린 게임을 자동으로 무승부로 변환하지 말고 미완료 처리와 재실행 정책을 정한다. 50수·반복 등 체스 규칙 판정은 선택한 러너의 동작을 검증하고 고정한다.

필수 결과물은 전체 PGN, pair/opening ID, WDL·pentanomial 빈도, 실제 수당 시간, 타임아웃·크래시·무효 기록, 엔진/가중치/설정/책 파일 해시, 하드웨어·드라이버, 난수 seed, 통계 방법·CI·중단 이유다. 결과를 숫자 하나가 아니라 다시 실행할 수 있는 실험 기록으로 남긴다.

## 3. 비용 모델과 핵심 연구 가설

### 3.1 FLOPs는 수단이다

평가 지연의 설명용 근사는 `t ≈ max(FLOPs/유효연산속도, 이동바이트/유효대역폭) + 실행·동기화 비용`이다. 엔진에는 여기에 규칙·탐색·큐 대기가 더해진다. 따라서 연산 수를 줄이거나, 연산 수가 늘어도 메모리 이동·대기·중복 작업을 줄이는 경로를 모두 허용한다. [^R34]

이전 대화의 ‘64토큰, d=256, FFN=4d에서 attention 행렬 곱이 주요 MAC의 약 4%’는 **가상 구조에 대한 계산 예시**다. 실제 LC0의 비중이 아니다. LC0 자료는 FFN 확대의 제한적 이득도 보고하므로 실제 선택 모델의 projection·FFN·GAB·head·메모리 시간을 따로 재야 한다. [^R01]

### 3.2 네 가지 가설

| ID | 가설 | 핵심 비교 |
|---|---|---|
| H1 | 변경분 친화적 특징이 전체 재인코딩보다 빠르다. | 동일 모델의 완전 재계산 vs 증분 재계산 |
| H2 | 작은 전역 잠재 공간이 판단력 대비 비용을 줄인다. | 같은 학습 예산·실제 추론 시간의 칸-token 기준선 |
| H3 | 부모 잠재 상태를 자식의 좋은 초기값으로 쓸 수 있다. | cold start vs warm start, 같은 총시간 |
| H4 | 유용한 작업의 지연을 줄이는 큐·선행 평가가 탐색을 개선한다. | 같은 네트워크·시간의 기존 스케줄러 |

H1은 수학적으로 정확한 재사용부터 시작한다. H2/H3는 학습된 근사다. H4는 개별 평가가 같더라도 탐색 순서를 바꿀 수 있다. 이 구분을 실험 ID와 결과 설명에 유지한다.

### 3.3 세 가지 변경 유형

**E형: 의미 보존 최적화.** 연산 융합·정확한 캐시·정확한 차분 갱신. 수학적 결과 유지와 부동소수점 비트 일치는 다를 수 있으므로 허용 오차를 정의한다.

**A형: 근사·모델 변경.** 양자화, 잠재 압축, 토큰 병합, warm-start 조기 종료. 출력 오차·치명적 실수·같은 시간 대국을 검증한다.

**S형: 탐색·스케줄 변경.** 어떤 평가를 언제 수행하고 얼마나 정밀하게 할지 변경. 버려진 계산과 critical-path 지연을 포함해 평가한다.

## 4. 제안 엔진 구조와 책임 경계

### 4.1 계산 흐름

아래는 기존 재사용 중심 구조 가설이다. v0.2.0의 G 경로는 먼저 기존 LC0를 계측하며, 증분 특징·warm-start 채택은 GPU 효율 검증 뒤에 결정한다. 14~17장의 트랙 구분을 우선한다.

정확한 상태 → 증분 특징 → 작은 전역 잠재 모듈 → policy/WDL·후보 평가 → 탐색·계산 예산 제어 → 실제 착수.

선택한 자식은 부모의 특징·잠재 상태에서 출발할 수 있다. 단, 전역 정보를 이미 섞은 깊은 표현이 자동으로 재사용 가능하다고 가정하지 않는다. 중요한 상태에서는 완전 재계산 경로가 같은 자체 모델 안에 존재해야 한다. 정상 시간 안에 검증·복구하지 못한 내부 오류는 로그에 남기며, 평가 중 타 엔진을 몰래 호출해 복구하지 않는다.

### 4.2 모듈 계약

| 모듈 | 책임 | 책임이 아닌 것 |
|---|---|---|
| Rules / State | 합법 수, 상태 전이, 이력, 종료 판정 | 신경망 추정으로 규칙 대체 |
| Encoder | 칸·기물·관계 특징과 MoveDelta 구성 | 탐색 방문 통계 변경 |
| Feature Cache | 키·버전·수명·정밀도에 맞는 특징 저장 | 근사 값을 정확한 상태로 취급 |
| Evaluator | policy, WDL, 선택적 Q·불확실성 출력 | 직접 착수·대국 판정 |
| Refinement Controller | 추가 반복·완전 재계산 요청 | 근거 없는 후보 영구 제거 |
| Search | 탐색 선택·백업·루트 착수 결정 | 모델별 입력 형식 강제 |
| Runtime Scheduler | 큐·배치·취소·자원·마감 관리 | 취소된 결과의 무조건 반영 |
| Trainer / Dataset | 교사·자가대국 데이터와 학습 | 최종 holdout으로 튜닝 |
| Arena / Statistics | 대국·시계·PGN·pair 통계 | 엔진 내부의 자체 승패 판정 신뢰 |

### 4.3 입출력 계약

`PositionState`는 보드뿐 아니라 차례, 캐슬링 권리, 앙파상, 규칙 카운터, 필요한 반복·입력 이력을 포함한다. `MoveDelta`는 일반 이동·포획·캐슬링·앙파상·승격을 구분하고 제거/추가 특징과 전역 조건 변화를 기록한다.

`EvalRequest`에는 상태 식별자, 모델·인코딩 버전, 합법 수 목록/순서 해시, 정밀도·반복 예산, deadline, 선택적 부모 캐시 handle을 넣는다. `EvalResult`에는 같은 요청 ID, 같은 순서의 policy, `W,D,L`, 평가 관점, 완료 상태, 정밀도·반복 수, 캐시 유래, 필요하면 예측 오차 지표를 넣는다.

평가 관점은 **현재 차례 플레이어 기준**을 권고한다. WDL은 유한하고 합이 1이어야 하며, 종료 상태는 규칙 모듈에서 처리한다. 부모→자식 백업 시 승/패의 관점 교환을 명시한다. policy는 합법 수에만 대응하고 promotion 종류를 구별한다. 후보 수 목록의 순서·패딩을 바꿨을 때 state value가 달라지지 않아야 한다.

### 4.4 캐시 불변식

캐시 키는 최소한 실제 모델 입력을 식별할 수 있어야 한다. 보드 배치만 같은 상태, 다른 history-fill, 다른 모델·정밀도·인코딩의 결과를 섞지 않는다. 반복 판정을 위한 키와 신경망 입력 캐시 키는 요구 정보가 다를 수 있으므로 목적을 분리한다.

**완전 재계산과 같은 결과를 내는 캐시**와 **경로에 따라 달라지는 근사 잠재 상태**를 다른 타입·namespace로 다룬다. warm-start 상태가 아직 경로 독립적이지 않다면 그 결과를 정확한 transposition 평가로 공유하지 않는다. provenance나 부모 상태를 구별하고, 확정한 fresh 평가로만 정규 캐시를 채우는 방식을 우선한다.

평가 결과 재사용은 MCTS 방문 횟수를 새로 만들어 내는 행위가 아니다. 다른 parent edge의 통계·virtual loss·in-flight 수는 별도 관리한다. 취소된 작업과 늦게 도착한 결과가 현재 루트·새 모델 상태를 오염시키지 않도록 generation ID를 검사한다.

### 4.5 기존 기반 재사용 경로

**경로 A:** LC0의 기존 모델·검색을 유지한 실행/캐시/스케줄 실험. **경로 B:** 같은 데이터로 학습한 소형 기준선과 새로운 입력·잠재 구조의 실험. 가중치 호환이 깨지는 변경은 입력 토크나이저의 ‘단순 교체’로 기록하지 않는다. [^R57] [^R02]

프로토타입 학습은 Python 계열을 권고하되 엔진 언어는 미확정이다. LC0 코드를 직접 기반으로 하면 기존 네이티브 생태계를 우선 검토한다. Ceres는 독립 비교·설계 참고 후보이지 반드시 의존해야 하는 구성요소가 아니다. [^R05]

코드·가중치·교사 생성 데이터·오프닝 책은 각각 출처와 라이선스를 기록한다. LC0 COPYING 하나로 모든 자산의 재배포 권리를 판단하지 않는다. 포크 여부와 최종 배포 라이선스는 구현 전에 정하고, 이번 단계에서는 저장소를 생성하거나 외부 코드를 복사하지 않는다. [^R58]

## 5. 후보 A — 입력·관계·공통 인코딩

이 장은 첫 논의의 tokenizer·Transformer·GNN·전문가 아이디어를 보존한다. 입력 표현만 바꾸는 실험과 모델 본체·출력층을 바꾸는 실험을 분리한다.

### A01. 64칸 토큰 + 상대 위치·체스 관계

**근거:** 체스 근거 / **순서:** 우선: 기준선 / **변경:** A

**원리·출처.** LC0/Chessformer는 칸 토큰과 체스 관계를 반영하는 attention 구조를 사용한다. [^R01] [^R02]

**RoveZero 적용 가설.** 소형 square-token Transformer를 학습 기준선으로 두고, 좌표·이동선·차단·핀 등의 관계를 하나씩 추가한다. 2D CNN은 보조 비교군으로 남긴다.

**위험·최소 실험.** 이미 존재하는 GAB/smolgen/RPE를 누락한 약한 기준선과만 비교하지 않는다. 관계 계산의 CPU/GPU 비용과 같은 시간 대국을 함께 측정한다. 칸 토큰이 항상 최적이라는 가정도 하지 않는다.

**하드웨어 적합성 — 추론치·미측정.** CPU: **조건부** / GPU 직접: **높음** / GPU 중심 시스템 활용: **높음**. 권장 배치: G: GPU 평가. 고정 64칸 dense 계산과 묶음 실행에 적합할 것으로 본다. 작은 모델·배치 1에서는 CPU도 비교하고, 관계 입력 생성 비용을 포함한다.

### A02. 기물 entity-token과 안정적인 식별자

**근거:** 체스 관련 표현 연구 + 적용 가설 / **순서:** 후속 / **변경:** A

**원리·출처.** 기물·좌표·관계를 명시하는 표현은 칸 중심 표현과 다른 분해 방식이다. 그래프 체스 연구도 관계 중심 표현의 후보 근거가 된다. [^R02] [^R07]

**RoveZero 적용 가설.** 기물 토큰에 종류·색·좌표를 넣고 전역 상태와 빈칸·이동선 정보는 별도로 제공한다. 한 수 뒤 무효화되는 특징 수를 줄이는 안정적인 토큰 배치를 연구한다.

**위험·최소 실험.** 빈칸·통제 공간을 잃을 수 있고 padding·재정렬이 절약을 지울 수 있다. 동일 토큰 예산보다 실제 지연과 판단력을 비교한다. 추적용 ID가 같은 상태의 의미를 경로에 따라 바꾸지 않게 한다.

**하드웨어 적합성 — 추론치·미측정.** CPU: **조건부** / GPU 직접: **조건부** / GPU 중심 시스템 활용: **조건부**. 권장 배치: G/H: 혼합. 토큰 감소가 padding·정렬·gather 비용을 넘는지 미정이다. 안정된 ID는 증분 갱신에 도움이 될 수 있지만 GPU의 일정한 shape를 해칠 수 있다.

### A03. 칸·기물 혼합 표현과 Transformer–GNN

**근거:** 체스 근거 / **순서:** 후속 / **변경:** A

**원리·출처.** AlphaGateau 계열은 그래프 표현을 체스 강화학습에 사용한다. 모델의 확장성과 최고 수준의 Elo는 별개의 지표다. [^R07] [^R02]

**RoveZero 적용 가설.** 정확한 64칸 표현을 남기고 기물 간 공격·방어·차단 관계를 보조 edge로 제공한다. 관계형 모듈을 전체 GNN 교체보다 작은 실험 단위로 시작한다.

**위험·최소 실험.** 관계 중복·동적 그래프 생성·희소 실행 비용을 측정한다. 표준 체스에서의 이득을 증강체스 확장성으로 대신 입증하지 않는다.

**하드웨어 적합성 — 추론치·미측정.** CPU: **조건부** / GPU 직접: **조건부** / GPU 중심 시스템 활용: **조건부**. 권장 배치: G/H: CPU 관계 생성 또는 GPU dense mask. 작은 동적 그래프는 불규칙하다. sparse message passing뿐 아니라 64×64 관계 mask로 바꾼 dense 기준도 비교한다.

### A04. BPE에서 차용한 전술·구조 패턴 토큰

**근거:** 타 분야 근거 + 체스 적용 가설 / **순서:** 보류: 소규모 탐색 / **변경:** A

**원리·출처.** BPE/subword는 자주 반복되는 단위를 압축해 표현한다. 전술 패턴을 묶는 것은 원문의 검증 결과가 아니라 새로운 적용이다. [^R59]

**RoveZero 적용 가설.** 정확한 보드를 보존하면서 폰 구조·전술 모티프를 보조 특징으로 제공한다. FEN/PGN 문자열 토큰화는 비교군이나 데이터 인터페이스로만 둔다.

**위험·최소 실험.** 패턴이 같아 보여도 합법성·차례·수비 자원 차이가 치명적일 수 있다. 패턴 탐지 비용, 누락, 데이터 편향을 검사한다. 매크로 수는 반드시 ply별로 실행·검증한다.

**하드웨어 적합성 — 추론치·미측정.** CPU: **조건부** / GPU 직접: **낮음** / GPU 중심 시스템 활용: **조건부**. 권장 배치: H/C: CPU 특징 또는 오프라인. 작은 상태에서 패턴 탐지·가변 토큰 처리는 GPU 호출을 정당화하기 어렵다고 본다. 미리 계산한 보조 특징은 GPU 입력에 사용할 수 있다.

### A05. Perceiver식 작은 전역 잠재 공간

**근거:** 타 분야 근거 / **순서:** 우선: 구조 실험 / **변경:** A

**원리·출처.** Perceiver IO는 입력·출력 크기와 깊은 내부 계산의 크기를 분리한다. [^R35]

**RoveZero 적용 가설.** 얕은 정확 보드 특징을 유지하고 8/16/32개 잠재 슬롯에서 비싼 계산을 수행하는 후보를 비교한다. 필요할 때 보드에 다시 cross-attention하고 policy/WDL을 질의로 만든다.

**위험·최소 실험.** 잠재 병목이 전술 정보를 지울 수 있고 cross-attention 비용도 남는다. 잠재 슬롯 수, 다시 읽는 빈도, 실제 배치 지연을 분리해 실험한다. 숫자는 확정 구조가 아니다.

**하드웨어 적합성 — 추론치·미측정.** CPU: **조건부** / GPU 직접: **높음** / GPU 중심 시스템 활용: **높음**. 권장 배치: G: GPU 평가. 고정 잠재 슬롯은 FFN 폭과 깊은 계산량을 줄이기 쉽다. 너무 작은 행렬과 cross-attention 재독해가 이득을 상쇄할 수 있다.

### A06. 형제 후보의 공통 인코딩 + 행동 디코더

**근거:** 관련 원리 + 적용 가설 / **순서:** 후속 / **변경:** A/S

**원리·출처.** 구조화된 질의 출력과 행동가치 학습은 비싼 상태 인코딩을 여러 후보가 공유하는 출발점이다. [^R35] [^R04]

**RoveZero 적용 가설.** z=E(s)를 한 번 계산하고 Q(s,a)=D(z,a,MoveDelta)로 후보 초기값을 만든다. 실제 확장되는 자식만 정밀 재평가한다. policy prior와 방문에서 얻은 Q를 구분한다.

**위험·최소 실험.** 비용 mC→C+mc는 m개 후보를 실제로 평가할 때의 설명식이다. 사용하지 않을 자식을 모두 계산하면 손해이며, Q 예측을 방문 횟수로 전환하지 않는다. hard counter-move 오류를 검사한다.

**하드웨어 적합성 — 추론치·미측정.** CPU: **조건부** / GPU 직접: **높음** / GPU 중심 시스템 활용: **조건부**. 권장 배치: G: GPU 공유 인코더·후보 head. 같은 부모의 실제 필요한 후보를 묶으면 공통 계산을 나눌 수 있다. 미사용 후보까지 계산하면 높은 커널 효율에도 엔진은 약해질 수 있다.

### A07. 작은 MoE·국면별 전문가

**근거:** 체스 근거와 반대 근거 모두 있음 / **순서:** 후속: 낮은 우선도 / **변경:** A/S

**원리·출처.** M²CTS는 체스 전문가 결합을 연구한다. 반면 LC0의 일부 MoE 실험은 뚜렷한 개선을 보이지 않았다고 보고한다. 두 구조와 기준선은 같지 않다. [^R06] [^R01]

**RoveZero 적용 가설.** 먼저 일반 모델을 학습한 뒤 공유 본체에 소수의 전문가나 전문 head를 붙인다. 오프닝/중반/엔드게임 또는 구조별 분류는 각각 독립 가설로 취급한다.

**위험·최소 실험.** 희소 데이터·라우팅 비용·전체 VRAM·전문가 전환의 평가 불연속을 측정한다. 총 파라미터와 활성 연산량을 모두 보고하고 dense 기준선과 같은 시간에 비교한다.

**하드웨어 적합성 — 추론치·미측정.** CPU: **조건부** / GPU 직접: **조건부** / GPU 중심 시스템 활용: **조건부**. 권장 배치: G/H: 그룹별 실행. 작은 전문가 다수는 배치를 분할한다. 소수 정적 head와 grouped GEMM을 먼저 비교하고 총 가중치 VRAM을 포함한다.

## 6. 후보 B — 변경분 계산·캐시·메모리

재사용 가능한 부분을 먼저 설계하고 저장 방식을 선택한다. 기존 양방향 Transformer의 모든 층 KV를, 바뀌지 않은 칸이라는 이유만으로 재사용하는 방식은 허용하지 않는다.

### B01. DeltaCNN·NNUE에서 확장한 증분 특징

**근거:** 체스·영상 근거 / **순서:** H·C 우선, G 조건부 후속 / **변경:** E→A

**원리·출처.** NNUE는 증분 accumulator의 체스 선례이고, DeltaCNN은 영상의 변경분을 실제 희소 실행으로 연결한다. [^R03] [^R21]

**RoveZero 적용 가설.** 합산·국소 특징에서 제거된 기여를 빼고 추가된 기여를 더한다. h(s)=Σe(f)라면 h(s′)=h(s)−Σremoved+Σadded다. 이후 작은 전역 모듈을 재계산한다.

**위험·최소 실험.** 등식은 그렇게 정의한 특징층에 대한 것이지 임의의 깊은 attention 전체에 대한 것이 아니다. 완전 재계산과 독립 구현으로 비교하고 앙파상·캐슬링·승격·장거리 선 개방을 포함한다.

**하드웨어 적합성 — 추론치·미측정.** CPU: **높음** / GPU 직접: **낮음~조건부** / GPU 중심 시스템 활용: **조건부**. 권장 배치: H/C 우선; G는 별도 실험. 단일 경로의 작은 add/sub는 CPU에 유리할 가능성이 크다. GPU는 많은 노드의 delta를 합치고 특징을 상주시킬 때에만 별도 이득을 기대한다.

### B02. Self-adjusting computation·differential dataflow

**근거:** 타 분야 근거 / **순서:** 후속 / **변경:** E

**원리·출처.** 일반 프로그램·데이터 처리에서 의존성을 추적하고 입력 변경을 필요한 계산으로 전파한다. [^R22] [^R23]

**RoveZero 적용 가설.** 어떤 칸·기물·이동선이 어떤 특징을 무효화하는지 추적하고 변경된 관계만 다시 계산한다. 고정된 작은 의존성 표와 동적 그래프를 비교한다.

**위험·최소 실험.** 8×8 보드에서는 bookkeeping이 전체 재계산보다 비쌀 수 있다. 전체 프레임워크 도입을 전제로 하지 않고 정적 특화 구현과 비교한다. 누락 의존성은 즉시 정확성 실패다.

**하드웨어 적합성 — 추론치·미측정.** CPU: **높음** / GPU 직접: **낮음** / GPU 중심 시스템 활용: **조건부**. 권장 배치: H/C: CPU 의존성 관리. 작은 의존 그래프의 분기·메타데이터 추적은 host가 유리하다고 본다. 전역 관계 재계산을 실제로 줄이는지 확인한다.

### B03. 선형 attention의 갱신 가능한 관계 요약

**근거:** 타 분야 근거 / **순서:** 후속 / **변경:** A, 내부 갱신은 E 가능

**원리·출처.** Linear Transformer는 커널 특징과 합산 형태로 attention 계산을 재구성한다. [^R30]

**RoveZero 적용 가설.** A=Σφ(kᵢ)vᵢᵀ, b=Σφ(kᵢ)를 저장하고 독립적인 기물 기여만 제거·추가한다. 전체 Transformer 대체보다 작은 관계 메모리부터 검증한다.

**위험·최소 실험.** k/v가 이미 전역 문맥에 의존하면 대부분 다시 계산해야 한다. softmax attention과 동일한 결과는 아니며, 요약 행렬 크기·분모 안정성·전술 품질을 함께 검사한다.

**하드웨어 적합성 — 추론치·미측정.** CPU: **조건부** / GPU 직접: **조건부** / GPU 중심 시스템 활용: **조건부**. 권장 배치: G/H: 상주 요약·묶음 갱신. 낮은 rank와 충분한 갱신 묶음이 필요하다. 한 기물의 outer product마다 GPU를 호출하지 않고 재계산 dense 기준과 비교한다.

### B04. MLA식 저차원 잠재 캐시

**근거:** 타 분야 근거 / **순서:** 후속 / **변경:** A

**원리·출처.** DeepSeek-V2의 MLA는 KV를 낮은 차원의 잠재 표현으로 다루는 구조다. [^R26]

**RoveZero 적용 가설.** 노드별 모든 층 상태 대신 작은 잠재 벡터와 복원에 필요한 메타데이터를 저장한다. 독립 블록, 루트 근처, 재방문 가능성이 높은 노드에 선택적으로 적용한다.

**위험·최소 실험.** 압축률보다 재구성 비용·캐시 miss·같은 VRAM에서의 실제 처리량이 중요하다. 기존 LC0에 호환되는 손실 없는 파일 형식 변경이라고 취급하지 않는다.

**하드웨어 적합성 — 추론치·미측정.** CPU: **조건부** / GPU 직접: **조건부** / GPU 중심 시스템 활용: **조건부**. 권장 배치: G: GPU 잠재 캐시. GPU에 상주한 낮은 차원 상태의 복원·다음 연산을 묶을 때 후보가 된다. CPU↔GPU 왕복과 경로별 상태 저장량은 별도 부담이다.

### B05. KIVI식 분포 인식 캐시 양자화

**근거:** 타 분야 근거 / **순서:** 후속 / **변경:** A

**원리·출처.** KIVI는 K와 V의 분포에 맞춰 서로 다른 양자화 축을 사용한다. [^R24]

**RoveZero 적용 가설.** 체스 특징을 먼저 계측하고 채널별·토큰별·블록별 정밀도를 비교한다. cache 저장, unpack, dequant, 다음 연산을 하나의 경로로 측정한다.

**위험·최소 실험.** LLM에서의 2bit가 체스의 최적값이라는 가정은 금지한다. 재사용 횟수에 따른 누적 오차, 작은 WDL 차이, policy 순위 변화를 검증한다.

**하드웨어 적합성 — 추론치·미측정.** CPU: **조건부** / GPU 직접: **조건부** / GPU 중심 시스템 활용: **조건부**. 권장 배치: G/H: 캐시와 다음 연산의 공동 설계. 저비트 unpack·scale 처리까지 지원하는 커널이 필요하다. 단순 INT8·FP16 기준보다 느릴 가능성도 남긴다.

### B06. TurboQuant·회전 기반 벡터 압축

**근거:** 타 분야 근거·상충 비교 존재 / **순서:** 후속 / **변경:** A

**원리·출처.** TurboQuant는 회전·양자화로 벡터 오차를 다룬다. 실제 vLLM 보고와 RaBitQ 비교 연구는 정확도·속도 우위가 조건에 좌우됨을 보여 주는 반대 자료다. [^R25] [^R61] [^R62]

**RoveZero 적용 가설.** 자주 읽는 잠재 캐시의 저장·전송 비용이 병목일 때 실험한다. 비트 수별로 FP16/BF16 또는 단순 INT8 캐시와 비교한다.

**위험·최소 실험.** 회전·복원 비용이 절약보다 클 수 있다. 저장량, 캐시 hit당 지연, 총 엔진 시간, tail error를 함께 보고한다. 단일 논문의 무손실·배속 표현을 체스 성과로 복사하지 않는다.

**하드웨어 적합성 — 추론치·미측정.** CPU: **조건부** / GPU 직접: **조건부** / GPU 중심 시스템 활용: **조건부**. 권장 배치: G/H: 메모리 병목 확인 후. 회전과 복원의 연산 비용 때문에 압축률로 속도를 판단하지 않는다. cache hit당 지연과 총 엔진 시간으로 판정한다.

### B07. H2O식 가치 기반 캐시 교체

**근거:** 타 분야 근거 / **순서:** 후속 / **변경:** E/S

**원리·출처.** H2O는 모든 KV를 보관하는 대신 중요 항목을 남기는 정책을 연구한다. [^R27]

**RoveZero 적용 가설.** 재사용 확률×재계산 비용÷저장 바이트를 출발점으로 캐시 보존 가치를 추정한다. 단순 LRU/LFU·깊이 기반 보존과 비교한다.

**위험·최소 실험.** attention 값이 곧 미래 재사용 가치라는 가정은 하지 않는다. eviction은 원본 상태에서 재계산 가능해야 하며, 교체 정책 관리 비용을 계측한다.

**하드웨어 적합성 — 추론치·미측정.** CPU: **높음** / GPU 직접: **낮음** / GPU 중심 시스템 활용: **높음**. 권장 배치: G/H: CPU 캐시 정책. 정책 갱신은 CPU에 두고 비싼 GPU 재평가를 절약하는 방식이 자연스럽다. 관리 비용과 적중률 분포를 확인한다.

### B08. PagedAttention·RadixAttention식 블록 공유

**근거:** 타 분야 근거 / **순서:** 후속 / **변경:** E/S

**원리·출처.** PagedAttention은 블록 메모리 관리, SGLang은 공통 접두 계산 재사용을 제공한다. [^R28] [^R29]

**RoveZero 적용 가설.** 같은 특징 블록을 immutable handle로 공유하고 변경 블록만 copy-on-write한다. 공통 조상·같은 실제 입력의 평가를 중복 요청 제거와 연결한다.

**위험·최소 실험.** 경로 접두가 같다는 사실만으로 보드 Transformer의 깊은 상태가 동일한 것은 아니다. 참조 수·수명·취소·모델 버전을 검증하고 정책 통계와 캐시를 분리한다.

**하드웨어 적합성 — 추론치·미측정.** CPU: **높음** / GPU 직접: **조건부** / GPU 중심 시스템 활용: **높음**. 권장 배치: G/H: CPU 메타데이터+GPU pool. 작은 공유 handle 관리는 CPU, 규칙적인 블록 복사·읽기는 GPU 후보다. 참조 수·취소·모델 버전 때문에 동기화가 커질 수 있다.

### B09. Mamba·Gated Delta Networks의 작은 순환 상태

**근거:** 타 분야 근거 / **순서:** 보류: 비교 후보 / **변경:** A

**원리·출처.** 선택적 상태 공간·delta-rule 모델은 긴 입력을 작은 상태로 갱신한다. [^R15] [^R51]

**RoveZero 적용 가설.** 보드 전체를 대체하기보다 과거 움직임 요약이나 잠재 보정 초기값에 제한적으로 사용한다. 정확한 보드와 규칙 이력은 별도로 남긴다.

**위험·최소 실험.** 순서 의존 갱신은 제거·추가 가능한 합산 캐시와 다르다. 64토큰의 짧은 입력에서는 긴 시퀀스 장점이 작을 수 있고, transposition 경로별 편향을 검사해야 한다.

**하드웨어 적합성 — 추론치·미측정.** CPU: **조건부** / GPU 직접: **조건부** / GPU 중심 시스템 활용: **조건부**. 권장 배치: G/H: 잠재 보정 또는 이력. 작은 순차 state update는 CPU에도 맞고 병렬 학습은 GPU에 맞을 수 있다. 학습 적합성을 온라인 단일 경로 속도로 치환하지 않는다.

## 7. 후보 C — 반복 추론·계산량 배분·예측 실행

이 장의 핵심은 ‘무조건 더 오래 생각’이 아니라 ‘추가 계산의 효용이 높은 곳을 찾기’다. 확실한 무승부와 무지로 인한 평균 평가 0을 구분한다.

### C01. 추가 계산의 가치 예측

**근거:** 체스 관련 근거 + 적용 가설 / **순서:** 우선: 핵심 / **변경:** A/S

**원리·출처.** Ceres에는 불확실성·향후 변동성 보조 출력과 uncertainty boosting의 선례가 있다. [^R05] [^R41]

**RoveZero 적용 가설.** 작은 예산과 큰 예산의 평가를 짝지어 최선수 변경·regret 감소를 예측한다. 제어기는 다음 노드 확장과 현재 노드 정밀화 중 더 유익한 계산을 고른다.

**위험·최소 실험.** policy entropy나 평가 0을 난이도로 치환하지 않는다. 제어기 지연을 포함하고 최소 탐색 경로를 남긴다. 깊은 교사 판단도 확정 정답이 아니므로 안정성을 기록한다.

**하드웨어 적합성 — 추론치·미측정.** CPU: **높음** / GPU 직접: **조건부** / GPU 중심 시스템 활용: **높음**. 권장 배치: G/H: 작은 host 제어기 또는 배치 head. 배분 결정 자체는 작은 CPU 계산으로 충분할 수 있다. GPU 보조 head를 쓰면 기존 평가와 함께 출력하고 매 결정마다 왕복하지 않는다.

### C02. 공유 recurrent block의 잠재 추론

**근거:** 타 분야 근거·체스 해석 참고 / **순서:** 후속: 핵심 연구 / **변경:** A/S

**원리·출처.** Recurrent Depth는 문장을 늘리는 대신 같은 블록의 반복으로 test-time compute를 확장한다. [^R08] [^R09]

**RoveZero 적용 가설.** 반복 1/2/4/8 단계의 policy/WDL을 함께 학습한다. 쉬운 상태는 일찍 종료하고 어려운 상태만 더 반복하는 anytime evaluator를 만든다.

**위험·최소 실험.** 가중치 공유는 파라미터를 줄일 뿐 반복 연산을 없애지 않는다. 추가 반복과 실제 탐색 확장을 같은 벽시계 예산에서 비교한다. 내부 look-ahead 근거는 성능 보장이 아니다.

**하드웨어 적합성 — 추론치·미측정.** CPU: **조건부** / GPU 직접: **조건부** / GPU 중심 시스템 활용: **높음**. 권장 배치: G: 반복 예산별 GPU 큐. 블록은 dense여도 노드별 반복 수가 다르면 발산·작은 배치가 생긴다. 고정 1/2/4/8 단계 및 큐 분리를 먼저 비교한다.

### C03. 부모 잠재 상태로 초기화하는 자식 보정

**근거:** 관련 원리 + 신규 적용 가설 / **순서:** 후속: 핵심 연구 / **변경:** A

**원리·출처.** 반복 모델과 차분 계산의 결합에서 warm-start 원리를 차용한다. 이 구체적인 체스 구조의 성능은 미검증이다. [^R08] [^R21] [^R36]

**RoveZero 적용 가설.** z₀(s′)=U(z(s),MoveDelta), zₜ₊₁=R(zₜ,E(s′))로 자식의 해석을 수정한다. fresh 인코딩과 warm-start를 번갈아 감독하고 갱신 실패 시 자체 fresh 경로로 돌아간다.

**위험·최소 실험.** 작은 보드 변화가 작은 정답 변화를 뜻하지 않는다. 포획·희생·체크·선 개방과 같은 완전 상태의 다른 경로를 검사한다. 경로 의존 결과를 정확한 평가 캐시에 넣지 않는다.

**하드웨어 적합성 — 추론치·미측정.** CPU: **조건부** / GPU 직접: **조건부** / GPU 중심 시스템 활용: **조건부**. 권장 배치: G/H: 부모 잠재 상태 상주. 부모의 상태를 매번 전송하면 이득이 사라질 수 있다. 같은 ancestor·모델·예산별 locality와 fresh 경로를 함께 유지한다.

### C04. DEQ·Consistency distillation

**근거:** 타 분야 근거 / **순서:** 후속: 고위험 / **변경:** A

**원리·출처.** DEQ는 공유 변환의 고정점을, C-DEQ는 중간 상태에서 적은 단계로 평형에 접근하는 학습을 연구한다. [^R36] [^R37] [^R60]

**RoveZero 적용 가설.** 많은 반복의 자체 교사로 적은 단계 보정기를 학습한다. 반복 수를 상황에 맞게 조절하고 제한 시간 내의 마지막 유효 출력을 유지한다.

**위험·최소 실험.** 고정점 잔차가 작아도 체스 판단이 정확하다는 뜻은 아니다. 불안정 수렴·초기값 민감도·학습 비용을 보고하고 같은 시간의 더 깊은 명시적 탐색과 비교한다.

**하드웨어 적합성 — 추론치·미측정.** CPU: **조건부** / GPU 직접: **조건부** / GPU 중심 시스템 활용: **조건부**. 권장 배치: G: 고정 상한 반복; 연구 후속. 고정점 solver의 반복 수·동기화가 들쭉날쭉하다. distillation으로 짧은 고정 실행으로 바꿀 수 있는지가 관건이다.

### C05. DeepCache·TeaCache식 선택적 재계산

**근거:** 타 분야 근거 / **순서:** 후속 / **변경:** A/S

**원리·출처.** 확산 모델의 반복 단계에서 일부 특징을 재사용하고, 입력 변화로 재계산 필요성을 예측한다. [^R38] [^R39]

**RoveZero 적용 가설.** 현재 변경에 대해 캐시 갱신·추가 반복·완전 재계산 중 하나를 고르는 작은 gate를 둔다. 민감한 상태에서 보수적인 재계산 규칙과 비교한다.

**위험·최소 실험.** 체스의 전술적 불연속 때문에 변화량만으로 안전을 확정하지 않는다. 잘못된 재사용의 꼬리 위험과 gate 비용을 측정한다. 감사용 fresh 비교는 대국 시 공짜 계산이 아니다.

**하드웨어 적합성 — 추론치·미측정.** CPU: **높음** / GPU 직접: **조건부** / GPU 중심 시스템 활용: **조건부**. 권장 배치: G/H: gate는 host 또는 기존 head. 선택적 재계산이 배치를 잘게 쪼갤 수 있다. gate 자체보다 절약한 full 평가와 치명적 오재사용을 함께 측정한다.

### C06. Speculative decoding식 선행 평가

**근거:** 타 분야 근거 / **순서:** 후속 / **변경:** S, 공격적 방식은 A/S

**원리·출처.** 작은 모델의 제안을 큰 모델이 검증하여 순차 대기를 줄이는 원리다. [^R40]

**RoveZero 적용 가설.** 보수형은 다음에 필요할 포지션을 예측해 자기 생각 시간의 여유 자원으로 평가만 미리 준비한다. 공격형은 저정밀도 판단 후 선택적 정밀 검증을 별도 알고리즘으로 둔다.

**위험·최소 실험.** 원래의 동일 출력 분포 보장은 MCTS에 적용되지 않는다. 미사용 선행 계산·중요 요청 지연·취소를 측정한다. 미방문 노드의 방문 횟수를 선행 평가로 증가시키지 않는다.

**하드웨어 적합성 — 추론치·미측정.** CPU: **조건부** / GPU 직접: **조건부** / GPU 중심 시스템 활용: **조건부**. 권장 배치: G/H: 빈 평가 슬롯만 선행 사용. GPU가 포화이면 speculative 작업이 실요청을 밀어낸다. 적중률·취소·deadline을 기준으로 동적으로 제한한다.

### C07. Multi-fidelity best-arm identification

**근거:** 타 분야 근거 / **순서:** 후속 / **변경:** A/S

**원리·출처.** 비용·정확도가 다른 관측 수단을 사용하여 최선 선택지를 찾는다. [^R41]

**RoveZero 적용 가설.** 다른 후보를 볼지, 현재 후보를 더 깊게 볼지, 큰 모델로 확인할지를 함께 선택한다. 초기에 루트의 소수 후보에서만 실험한다.

**위험·최소 실험.** 체스 평가는 상관되고 깊이에 따른 편향이 미지수다. 논문의 가정을 확인하지 않고 유한 오차 경계나 안전한 영구 pruning을 주장하지 않는다.

**하드웨어 적합성 — 추론치·미측정.** CPU: **높음** / GPU 직접: **낮음~조건부** / GPU 중심 시스템 활용: **높음**. 권장 배치: G/H: CPU 예산 제어+GPU 평가. best-arm 결정은 host에서 처리하고 다양한 정밀도의 GPU 작업을 계획한다. 싸지만 편향된 관측을 확정 bound로 사용하지 않는다.

### C08. Mixture-of-Depths식 제한된 슬롯 갱신

**근거:** 타 분야 근거 / **순서:** 후속 / **변경:** A/S

**원리·출처.** 고정 계산 예산 내에서 일부 토큰만 특정 층을 통과시키는 동적 깊이 접근이다. [^R42]

**RoveZero 적용 가설.** 보드 정보는 보존하되 매 반복에서 갱신할 잠재 슬롯 수를 고정한다. 반복 예산별 큐에 넣어 GPU 실행 형태를 예측 가능하게 만든다.

**위험·최소 실험.** 덜 계산한 슬롯에 결정적 정보가 숨어 있을 수 있다. routing·gather/scatter 비용과 작은 dense 반복 기준선을 비교한다.

**하드웨어 적합성 — 추론치·미측정.** CPU: **조건부** / GPU 직접: **조건부** / GPU 중심 시스템 활용: **조건부**. 권장 배치: G: 고정 개수 슬롯·grouped 실행. 계산량이 고정돼도 선택·gather/scatter가 비용을 낸다. 작은 dense 모델이 더 빠를 수 있어 직접 비교한다.

## 8. 후보 D — 실제 실행·압축·컴파일러

FLOPs, 모델 크기, 캐시 압축률만으로 채택하지 않는다. 같은 장비에서의 전체 평가 경로와 실제 대국을 측정한다.

### D01. Roofline 기반 병목 분해

**근거:** 성능 모델 근거 / **순서:** 우선: 필수 계측 / **변경:** E

**원리·출처.** 연산 처리량과 메모리 대역폭을 함께 분석한다. [^R34]

**RoveZero 적용 가설.** projection·FFN·attention·GAB·head·입출력·큐 시간을 분해하고, shape별로 병목을 구분한다. FLOP와 MAC의 집계 관례도 기록한다.

**위험·최소 실험.** 개별 커널 최적화가 총시간에 미치는 상한을 먼저 계산한다. 낮은 FLOPs를 높은 하드웨어 활용률이나 Elo로 치환하지 않는다.

**하드웨어 적합성 — 추론치·미측정.** CPU: **해당 없음** / GPU 직접: **해당 없음** / GPU 중심 시스템 활용: **높음**. 권장 배치: 오프라인/개발 계측. 알고리즘 실행 위치를 고르는 도구다. CPU·GPU·전송·대기 프로파일을 모두 포함하며 추론 가속기로 점수화하지 않는다.

### D02. FlashAttention·연산 융합·CUDA Graph

**근거:** 타 분야·기존 LC0 구현 근거 / **순서:** 우선: 실행 실험 / **변경:** E/A

**원리·출처.** IO-aware 타일링·재계산과 하드웨어별 파이프라인이 중간 데이터 이동을 줄인다. LC0에도 관련 최적화가 존재한다. [^R31] [^R32] [^R63]

**RoveZero 적용 가설.** 실제 선택 모델의 64토큰·배치 분포에 맞춰 정규화·선형층·활성화·head를 묶고 실행 호출을 줄인다. FA4 같은 최신 구조는 원리만 차용한다.

**위험·최소 실험.** 특정 GPU 세대의 배속을 전용하지 않는다. 기존 최적화 활성 상태를 기준선에 반영하고 정밀도 변경이 섞이면 A형으로 따로 표시한다.

**하드웨어 적합성 — 추론치·미측정.** CPU: **일부 조건부** / GPU 직접: **높음** / GPU 중심 시스템 활용: **높음**. 권장 배치: G: GPU 커널·백엔드. CUDA Graph·타일링·융합은 GPU 후보이고 일반 fusion은 CPU에도 가능하다. LC0 기존 활성화 옵션과 동일하게 맞춘 뒤 추가분만 측정한다.

### D03. Wavefront 작업 큐·continuous batching

**근거:** 렌더링 원리 + 적용 가설 / **순서:** 우선: 실행 실험 / **변경:** S

**원리·출처.** 렌더링에서 작업별 큐를 사용하여 거대 커널의 분기·레지스터 부담을 줄인다. [^R33] [^R63]

**RoveZero 적용 가설.** 상태 전이·평가·반복 보정·백업을 역할별로 나누고 같은 shape·정밀도·예산의 평가를 묶는다. batch timeout과 중요한 요청의 deadline을 함께 고려한다.

**위험·최소 실험.** 최대 처리량과 최소 탐색 지연은 다르다. 큰 배치의 기다림, 중복 leaf, 오래된 루트 결과, GPU idle과 CPU 병목을 측정한다.

**하드웨어 적합성 — 추론치·미측정.** CPU: **높음** / GPU 직접: **조건부** / GPU 중심 시스템 활용: **높음**. 권장 배치: G: CPU 스케줄러+GPU 큐. 실행 단계 분리와 중첩이 핵심이다. GPU에서 모든 트리 제어를 실행한다는 뜻은 아니며 큐 대기·stale 결과를 함께 최적화한다.

### D04. RepVGG·FastViT 구조적 재매개변수화

**근거:** 비전 근거 / **순서:** 후속 / **변경:** E, 학습 구조는 A

**원리·출처.** 학습 때 풍부한 분기를 사용하고 추론 때 합칠 수 있는 선형·정적 연산을 단순화한다. [^R43] [^R44]

**RoveZero 적용 가설.** 지역 특징 추출기·고정 관계 mixing에 학습용 다중 분기를 두고 export에서 병합한다. 병합 전후 출력과 실행 시간을 비교한다.

**위험·최소 실험.** 동적 attention·입력 의존 분기·임의 비선형을 모두 합칠 수는 없다. 수학적 조건과 수치 오차를 검증한다.

**하드웨어 적합성 — 추론치·미측정.** CPU: **높음** / GPU 직접: **높음** / GPU 중심 시스템 활용: **조건부**. 권장 배치: G/H/C: export 시 정적 병합. 지원되는 선형·정적 분기를 병합하면 양쪽 추론이 단순해질 수 있다. 변경 전후 값과 전체 지연을 따로 검증한다.

### D05. Token Merging

**근거:** 비전 근거 / **순서:** 보류: 제한적 실험 / **변경:** A

**원리·출처.** ToMe는 비슷한 중간 토큰을 병합하여 이후 계산을 줄인다. [^R45]

**RoveZero 적용 가설.** 정확한 칸·기물 상태는 유지하고 보조 잠재 슬롯에서만 병합한다. 중간 슬롯 수를 줄이는 A05의 단순 고정 병목과 비교한다.

**위험·최소 실험.** 작은 차이가 유일한 방어를 결정할 수 있다. 병합 탐지 비용·전술 누락·복원 불가능한 정보 손실을 검사한다.

**하드웨어 적합성 — 추론치·미측정.** CPU: **조건부** / GPU 직접: **조건부** / GPU 중심 시스템 활용: **조건부**. 권장 배치: G: 보조 잠재 토큰에 제한. 토큰 병합 판단과 shape 변화가 GPU 이득을 없앨 수 있다. 정확한 보드 토큰은 남기고 고정 슬롯 축소와 비교한다.

### D06. 조건부 FFN·Fast Feedforward Networks

**근거:** 타 분야 근거 + 체스 반대 자료 / **순서:** 후속: 낮은 우선도 / **변경:** A

**원리·출처.** 라우팅으로 FFN의 일부만 실행한다. 다만 LC0의 FFN 확대·일부 MoE 실험은 제한적 효과를 보고했다. [^R46] [^R01]

**RoveZero 적용 가설.** 실측에서 FFN이 지배적일 때 작은 dense 대안과 비교한다. 하드웨어 친화적인 큰 블록 단위 선택을 우선한다.

**위험·최소 실험.** 희소 활성화가 작은 불규칙 커널을 만들면 느려진다. 라우팅 비용·활성 파라미터·전체 가중치 메모리와 동일 시간 Elo를 확인한다.

**하드웨어 적합성 — 추론치·미측정.** CPU: **조건부** / GPU 직접: **낮음~조건부** / GPU 중심 시스템 활용: **조건부**. 권장 배치: G/H/C: 큰 블록 단위 선택. 미세한 라우팅은 GPU에 불리하다고 본다. 균일한 큰 블록 단위와 실제 FFN 병목이 있는 경우에만 유력해진다.

### D07. SparseGPT·구조적 희소성

**근거:** 타 분야 근거 / **순서:** 후속 / **변경:** A

**원리·출처.** SparseGPT는 대형 모델 가중치 가지치기를 연구한다. [^R47]

**RoveZero 적용 가설.** 선택 하드웨어가 지원하는 구조적 패턴에서 calibration·필요한 재학습과 실제 sparse kernel을 함께 시험한다. dense 저차원 모델도 비교한다.

**위험·최소 실험.** 단순히 0을 많이 넣은 dense 행렬은 빨라지지 않을 수 있다. calibration 데이터 누출, 드문 전술 오류, fallback 커널 사용 여부를 검사한다.

**하드웨어 적합성 — 추론치·미측정.** CPU: **조건부** / GPU 직접: **조건부** / GPU 중심 시스템 활용: **조건부**. 권장 배치: G: 지원 희소 커널; C: SIMD 별도. 비정형 sparsity와 하드웨어 구조적 sparsity는 다르다. 지원 kernel·shape가 없으면 낮은 FLOPs에도 가속되지 않는다.

### D08. 양자화·Marlin·SageAttention식 실행

**근거:** 타 분야·기존 엔진 근거 / **순서:** 우선 또는 후속: 하드웨어 의존 / **변경:** A

**원리·출처.** 저비트 가중치·저정밀도 attention은 메모리와 연산을 줄일 수 있으며, 복원까지 포함한 커널 설계가 중요하다. [^R48] [^R49] [^R03]

**RoveZero 적용 가설.** FP32 검증 기준, 실용 FP16/BF16 기준, 지원되는 INT8/INT4 후보를 구분한다. policy/WDL head 등 민감 부위는 더 높은 정밀도 유지도 비교한다.

**위험·최소 실험.** 한 포지션이 64토큰이면 batch B의 행렬 행 수는 B뿐 아니라 B×64 등으로 달라진다. LLM 1-token decoding의 배속을 가져오지 않는다. PTQ/QAT의 학습·실행 비용을 모두 기록한다.

**하드웨어 적합성 — 추론치·미측정.** CPU: **높음** / GPU 직접: **높음(지원 형식)** / GPU 중심 시스템 활용: **높음**. 권장 배치: G/H/C: 각 ISA별 실행. CPU 정수 dot와 GPU tensor 연산의 유리한 형식이 다르다. head 정밀도·누산·dequant를 포함한 전체 경로로 비교한다.

### D09. BitNet식 극저비트 학습

**근거:** 타 분야 근거 / **순서:** 보류: 고위험 / **변경:** A

**원리·출처.** 가중치를 극저비트 표현으로 학습하는 구조다. [^R50]

**RoveZero 적용 가설.** 작은 메모리·CPU 실행이 별도 목표가 되었을 때 연구 트랙을 만든다. 같은 크기의 INT8 소형 모델과 비용 대비 성능을 비교한다.

**위험·최소 실험.** 기존 LC0 가중치를 단순 반올림하여 실력을 보존하는 방식이 아니다. 재학습·특화 커널·표현력 저하를 감수할 근거가 있어야 한다.

**하드웨어 적합성 — 추론치·미측정.** CPU: **조건부** / GPU 직접: **낮음~조건부** / GPU 중심 시스템 활용: **조건부**. 권장 배치: C 우선; G 전용 커널은 보존. 극저비트가 해당 GPU에서 직접 실행되지 않을 수 있다. CPU에서의 장점도 미검증이며 실제 packed 연산과 INT8 기준이 필요하다.

### D10. Ansor식 실행 계획 자동 탐색

**근거:** 컴파일러 근거 / **순서:** 후속 / **변경:** E

**원리·출처.** 타일링·병렬화·연산 순서 등 실행 계획을 자동 탐색한다. [^R52]

**RoveZero 적용 가설.** 실제 탐색에서 관찰한 shape·배치 분포를 가중치로 사용해 커널을 튜닝한다. 선택 하드웨어별 결과와 코드 생성 버전을 저장한다.

**위험·최소 실험.** 벤치마크 전용 shape에 과적합하지 않는다. 컴파일·튜닝 시간을 학습/개발 비용으로 따로 기록하고 실행 중 예상치 못한 재컴파일을 감시한다.

**하드웨어 적합성 — 추론치·미측정.** CPU: **해당 없음** / GPU 직접: **해당 없음** / GPU 중심 시스템 활용: **높음**. 권장 배치: 오프라인 CPU/GPU 코드 생성. 자동 튜닝은 개발 기법이다. 산출된 커널의 CPU/GPU 효과를 측정하며 튜닝 시간은 개발비에 별도 기록한다.

## 9. 후보 E — 학습·지식 전달·보조 연구

첫 논의에서 제안한 증류·학습 최적화·전문 적응·세계 모델·LLM 관련 항목을 빠뜨리지 않고 보존한다. 자연어 LLM 호출은 핵심 실시간 탐색 경로에서 제외한다.

### E01. 탐색 증류·반박 수·어려운 상태 채굴

**근거:** 체스 근거 / **순서:** 우선: 학습 기반 / **변경:** A

**원리·출처.** Searchless Chess는 강한 엔진의 행동·가치 정보를 학습하는 사례다. [^R04] [^R02]

**RoveZero 적용 가설.** 최선수 하나뿐 아니라 후보 분포·WDL·행동가치 차이·얕은 탐색의 오류·깊은 반박 수를 저장한다. 다른 교사의 불일치는 무작정 평균내기보다 추가 검토 데이터 선정에 쓴다.

**위험·최소 실험.** 교사 탐색도 유한하고 확신이 틀릴 수 있다. 교사 버전·예산·일관성·데이터 생성 비용을 기록한다. 교사 하나에 특화된 편향과 teacher ensemble 비용을 분리한다.

**하드웨어 적합성 — 추론치·미측정.** CPU: **오프라인** / GPU 직접: **오프라인 학습: 높음** / GPU 중심 시스템 활용: **높음**. 권장 배치: 오프라인 교사 생성+GPU 학습. CPU/GPU 교사 비용과 학습 비용을 분리한다. 학습 방식 자체에 온라인 GPU 직접 실행 점수를 주지 않는다.

### E02. WDL·분포형 가치·보조 목표

**근거:** 체스·강화학습 근거 / **순서:** 우선: 기본 head / 확장은 후속 / **변경:** A

**원리·출처.** 분류형 가치 학습과 체스의 WDL·불확실성 보조 출력에 선행 근거가 있다. [^R11] [^R05]

**RoveZero 적용 가설.** WDL을 기본 계약으로 두고 행동가치·최선수 안정성·추가 계산 효용·향후 위협을 별도 head로 비교한다. budget 조건부 calibration도 후보로 둔다.

**위험·최소 실험.** WDL의 무승부 확률과 인식 불확실성은 다르다. 추가 head의 계산비용과 loss 간 충돌을 측정하며 새 head를 붙인 것만으로 개선이라고 하지 않는다.

**하드웨어 적합성 — 추론치·미측정.** CPU: **조건부** / GPU 직접: **높음** / GPU 중심 시스템 활용: **높음**. 권장 배치: G/H: 평가와 함께 head 출력. WDL·보조 head를 기존 batch 안에서 계산하면 유리할 수 있다. 추가 head와 calibration 비용이 작다는 가정은 계측한다.

### E03. SOAP·AdamW와 학습 효율

**근거:** 타 분야·체스 프로젝트 자체 보고 / **순서:** 우선: 기준선 / SOAP는 후속 / **변경:** A: 학습 변경

**원리·출처.** SOAP는 고차 최적화와 Adam을 결합하며, Ceres도 수렴·학습 시간 실험을 보고한다. [^R10] [^R67] [^R05]

**RoveZero 적용 가설.** 기준 학습 recipe를 잠근 뒤 optimizer만 바꾸어 목표 품질까지의 실제 시간·VRAM·안정성을 비교한다. 동일 update 수와 동일 wall-clock 결과를 구분한다.

**위험·최소 실험.** 수렴 단계 감소가 추론 가속은 아니다. optimizer별 적절한 학습률 튜닝을 별도 세트에서 하며, 느린 step·추가 상태 메모리를 포함한다.

**하드웨어 적합성 — 추론치·미측정.** CPU: **오프라인** / GPU 직접: **오프라인 학습: 조건부** / GPU 중심 시스템 활용: **조건부**. 권장 배치: 오프라인 학습 전용. SOAP의 step 메모리·전처리 비용까지 비교한다. 추론 적합성은 해당 없으며 학습 개선을 커널 가속으로 표시하지 않는다.

### E04. 자기대국·RLVR·GRPO 차용

**근거:** 체스 강화학습·타 분야 근거 / **순서:** 후속 / **변경:** A/S

**원리·출처.** 체스는 규칙과 승패를 확인할 수 있는 환경이며 GRPO는 후보군 상대 보상으로 정책을 학습하는 원리를 제공한다. [^R16] [^R57]

**RoveZero 적용 가설.** 안정된 증류 모델 이후 자기대국을 추가한다. GRPO류는 policy 또는 계산 배분 제어기의 독립 실험으로 둔다. 원래 MCTS 정책 학습과 같은 비용으로 비교한다.

**위험·최소 실험.** 합법 수는 좋은 수와 다르고, 이길 가능성과 교사 점수를 혼합하면 보상 왜곡이 생길 수 있다. 그룹 생성 비용·보상 hacking·학습 불안정을 기록한다.

**하드웨어 적합성 — 추론치·미측정.** CPU: **오프라인** / GPU 직접: **오프라인 학습: 높음** / GPU 중심 시스템 활용: **조건부**. 권장 배치: 오프라인 자가대국·학습. self-play 실행과 optimizer를 구별한다. GRPO 그룹 생성 비용과 실제 학습 이득은 별도 가설이다.

### E05. LoRA·저랭크 전문화

**근거:** 타 분야 근거 / **순서:** 후속 / **변경:** A

**원리·출처.** 고정된 저랭크 갱신으로 일부 가중치만 학습한다. [^R12]

**RoveZero 적용 가설.** 데이터·학습 예산이 작을 때 국면 전문화나 실험용 adapter로 사용한다. 고정 어댑터는 검증 후 원본 가중치에 병합하여 실행 overhead를 줄일 수 있다.

**위험·최소 실험.** 표현 방식을 전면 변경해도 기존 가중치를 그대로 쓸 수 있게 해 주는 기술은 아니다. full fine-tuning과 비용·품질을 비교하고 병합 수치오차를 확인한다.

**하드웨어 적합성 — 추론치·미측정.** CPU: **조건부** / GPU 직접: **조건부** / GPU 중심 시스템 활용: **조건부**. 권장 배치: 오프라인 학습; 고정 병합 추론. 병합 가능한 LoRA는 추론 때 추가 경로가 없어질 수 있다. 동적 adapter 교체는 배치를 분할하므로 별도 평가한다.

### E06. FiLM·Hypernetwork의 조건부 적응

**근거:** 타 분야 근거 / **순서:** 보류: 필요 조건 확인 / **변경:** A

**원리·출처.** FiLM은 특징을 조건부 변환하고 Hypernetwork는 가중치를 생성한다. [^R13] [^R14]

**RoveZero 적용 가설.** 국면·반복 단계·예산 등 명시한 조건으로 계산을 조절한다. 표준 체스에서는 작고 정적인 모듈부터, 변형 체스 확장에서는 규칙 조건부 모듈을 별도 연구한다.

**위험·최소 실험.** 상태별 가중치는 하나의 고정 가중치로 일반적으로 병합되지 않는다. 생성·전송·컴파일·캐시 무효화 비용과 조건 경계의 불연속을 검사한다.

**하드웨어 적합성 — 추론치·미측정.** CPU: **조건부** / GPU 직접: **조건부** / GPU 중심 시스템 활용: **조건부**. 권장 배치: G/H: 가벼운 FiLM부터. FiLM과 상태별 큰 가중치 생성은 비용이 매우 다르다. Hypernetwork의 GPU 배치 효율을 정적 FiLM의 결과로 일반화하지 않는다.

### E07. MuZero식 학습된 잠재 전이

**근거:** 체스 포함 선행 근거 / **순서:** 보류: 진단 비교 / **변경:** A

**원리·출처.** MuZero는 잠재 전이 모델로 계획하는 접근을 연구했다. [^R17]

**RoveZero 적용 가설.** 정확한 규칙 전이는 유지하고 잠재 상태 업데이트를 더 좋은 초기값으로 사용한다. 명시적 상태 없이 전체 탐색을 대체하는 실험은 별도 트랙으로 둔다.

**위험·최소 실험.** 표준 체스의 정확한 상태 전이가 저렴하므로 이득을 먼저 입증해야 한다. 불법·존재하지 않는 상태의 상상, 장기 rollout 오차, 전술 손실을 검사한다.

**하드웨어 적합성 — 추론치·미측정.** CPU: **조건부** / GPU 직접: **조건부** / GPU 중심 시스템 활용: **조건부**. 권장 배치: G: 잠재 보정 연구. GPU rollout은 묶을 수 있지만 규칙 오류를 허용하는 실제 상태 대체는 하지 않는다. 정확한 싼 체스 전이보다 나은지 비교한다.

### E08. RAG·검색형 기억

**근거:** 타 분야 근거 / **순서:** 보류: 보조 기능 / **변경:** A/S

**원리·출처.** 외부 기억을 검색하여 모델의 입력이나 결과 생성에 활용한다. [^R18]

**RoveZero 적용 가설.** 정확히 같은 상태는 정확 캐시로, 비슷한 상태는 보조 참고 특징으로 분리한다. 폰 구조·정형 엔드게임의 검색 효용과 비용을 비교한다.

**위험·최소 실험.** 한 칸·차례·권리 차이로 결과가 달라질 수 있다. 검색 결과를 정답으로 취급하지 않고 데이터 누출·시간 비용·후보 순위 편향을 검사한다.

**하드웨어 적합성 — 추론치·미측정.** CPU: **높음** / GPU 직접: **낮음~조건부** / GPU 중심 시스템 활용: **조건부**. 권장 배치: H/C: host 검색; 큰 검색만 GPU. 작은 정확 캐시는 CPU가 자연스럽고 큰 벡터 검색은 GPU 후보다. 조회·전송·근사 검색 오차를 전부 계산한다.

### E09. Diffusion·Flow matching·국면 생성

**근거:** 타 분야 근거 / **순서:** 보류: 데이터 연구 / **변경:** A: 오프라인

**원리·출처.** 생성 경로와 consistency 학습은 반복 생성 또는 적은 단계 복원의 원리를 제공한다. [^R66] [^R60]

**RoveZero 적용 가설.** 희귀 구조의 학습용 상태·잠재 보정 데이터를 제안하는 보조 실험으로 둔다. 원래 보드 정보나 합법 이동열을 검증기로 보존한다.

**위험·최소 실험.** 겉으로 합법적으로 보이는 배치가 실제 도달 가능한 상태라는 보장은 없다. 생성 비용 대비 유효 데이터 증가와 학습 후 대국 이득을 측정한다.

**하드웨어 적합성 — 추론치·미측정.** CPU: **오프라인** / GPU 직접: **오프라인 학습/생성: 조건부** / GPU 중심 시스템 활용: **조건부**. 권장 배치: 오프라인 데이터 생성. 최종 추론 경로 해당 없음. 규칙·도달 가능성 검증은 별도이며 GPU 생성량으로 학습 효용을 대신하지 않는다.

### E10. 기계적 해석·인과 분석

**근거:** 체스 근거 / **순서:** 후속: 진단 / **변경:** A: 분석 도구

**원리·출처.** LC0의 미래 수 표현과 Chessformer의 해석 분석은 무엇을 모델이 표현하는지 조사하는 선례다. [^R09] [^R02]

**RoveZero 적용 가설.** 어떤 이동선·반박·역할 충돌을 놓치는지 진단하고 데이터와 관계 특징의 다음 가설을 만든다. 입력 교란과 내부 activation 개입을 구분한다.

**위험·최소 실험.** 설명 가능한 특징이 발견됐다고 Elo가 오르는 것은 아니다. 해석 도구를 성능 판정기로 승격하지 않는다.

**하드웨어 적합성 — 추론치·미측정.** CPU: **오프라인** / GPU 직접: **오프라인 분석: 조건부** / GPU 중심 시스템 활용: **조건부**. 권장 배치: 오프라인 진단. activation 분석의 장비 배치를 뜻할 뿐 추론 가속 점수가 아니다. 진단에서 얻은 후속 가설을 대국으로 검증한다.

### E11. LLM 연구에서 가져오는 구조화 궤적·다중 후보

**근거:** 타 분야·체스 LLM 연구 / **순서:** 보류: 오프라인 참고 / **변경:** A/S

**원리·출처.** Master Distillation, 체스 후학습 연구, self-consistency와 Tree of Thoughts는 교사 정보·궤적·다중 후보 사용을 연구한다. [^R19] [^R20] [^R64] [^R65]

**RoveZero 적용 가설.** 문장 생성을 넣지 않고 합법 이동열·반박 경로·잘못된 판단의 수정 기록을 학습한다. LLM은 검증된 변화를 설명하거나 데이터 후보를 정리하는 보조 역할에만 둔다.

**위험·최소 실험.** 후보 중 정답이 존재하는 비율과 실제 착수가 정답인 비율을 구분한다. 설명의 설득력·퍼즐 정답률을 대국 Elo로 대체하지 않는다. 검증되지 않은 LLM 라벨은 학습 정답이 아니다.

**하드웨어 적합성 — 추론치·미측정.** CPU: **오프라인** / GPU 직접: **오프라인 학습: 조건부** / GPU 중심 시스템 활용: **조건부**. 권장 배치: 오프라인 구조화 궤적 학습. 자연어 LLM을 온라인 착수 경로에 넣지 않는다. 학습 데이터 변화와 GPU 실행 형태 변화는 다른 실험이다.

### E12. AI 보조 실험 자동화

**근거:** 공학적 제안 / **순서:** 후속 / **변경:** E/S: 개발 절차

**원리·출처.** 후보 생성·실행 계획 탐색을 자동화하는 원리를 개발 과정에 적용한다. 이는 특정 에이전트가 체스 Elo를 개선했다는 외부 성과 인용이 아니다. [^R52]

**RoveZero 적용 가설.** 가설 등록, 설정 생성, 실행 기록 정리, 회귀 분석을 자동화하되 최종 대국 기준과 holdout 접근 권한을 고정한다. 실패한 실험도 삭제하지 않는다.

**위험·최소 실험.** 반복 실험으로 검증 세트에 과적합하기 쉽다. 자동 에이전트가 승격 기준·대국 결과·통계 중단 규칙을 임의 변경하지 못하게 한다.

**하드웨어 적합성 — 추론치·미측정.** CPU: **개발** / GPU 직접: **해당 없음** / GPU 중심 시스템 활용: **조건부**. 권장 배치: 개발 실험 관리. AI 에이전트·자동 실험은 런타임 알고리즘이 아니다. GPU 적합성 순위 대신 재현성과 holdout 관리로 평가한다.

## 10. 학습 계획과 데이터 계약

### 10.1 기준선부터 분리한다

첫 모델 실험은 같은 데이터·같은 출력 계약·같은 학습 예산의 소형 칸-token 기준선과 비교한다. 기존 LC0 가중치 기반 경로는 별도의 강한 외부 기준선이다. 자체 소형 모델보다 강해진 것을 LC0보다 강해진 것으로 표현하지 않는다.

입력 표현, 본체, policy head, loss, optimizer, 데이터 선택을 한 번에 바꾸지 않는다. 탐색 스케줄을 고정한 모델 실험과 모델을 고정한 스케줄 실험을 따로 수행한다. 최종 조합은 각 요소를 다시 제거하는 ablation으로 검증한다.

### 10.2 학습 데이터

초기 데이터에는 완전 상태 또는 이를 복원할 초기 상태+합법 이동열, 교사 ID·버전·예산, 후보별 정책/방문 수/WDL 또는 Q, 실제 대국 결과, 라벨 관점, 종료 이유를 기록한다. 가능하면 예산이 작은 분석과 큰 분석을 짝지어 추가 계산의 효용을 학습한다. [^R04] [^R57]

게임·opening 단위로 train/validation/holdout을 먼저 나누고, 같은 게임의 인접 포지션이 무작위 행 분할로 다른 세트에 흩어지지 않게 한다. 알려진 정확 중복과 가까운 transposition 누출도 감사한다. 외부 사전학습 데이터의 완전한 비중복성을 보장할 수 없다면 그 한계를 기록한다.

단순한 좋은 수 일치와 유일한 방어 수 누락은 다른 오류다. 전술·닫힌 구조·엔드게임·장거리 선 개방 등 실패군을 따로 유지하되, 최종 대국 포지션 분포를 보고 난 뒤 유리하게 재가중하지 않는다. 학습용 대칭 변환은 폰 방향·캐슬링·앙파상까지 같은 규칙 의미를 보존하는 경우만 허용한다.

### 10.3 잠재 보정 학습

후보 loss는 policy 증류, WDL, 후보 regret, fresh와 warm-start 사이의 일치, 반복별 일관성, 예측 계산 효용이다. 가중치는 미확정이며 loss를 추가할 때마다 비용·일반화를 비교한다. warm-start가 fresh 모델을 단순 복제하는지, 같은 시간에서 더 나은 결정을 돕는지 나눈다.

같은 완전 입력 상태가 다른 경로로 나타나는 데이터를 포함한다. 경로 독립성을 목표로 학습하더라도 수치적 정확성을 증명한 것은 아니므로 근사 캐시 타입을 유지한다. latent target이 미래 정보에만 의존해 실제 추론에서 제공할 수 없는 정보를 요구하지 않게 한다.

### 10.4 자기대국·훈련 비용

규칙·학습·추론 계약이 안정된 후 자기대국을 추가한다. 학습 시간뿐 아니라 교사 분석, 재분석, 자기대국, 데이터 저장, 하이퍼파라미터 탐색, 컴파일/커널 튜닝 비용을 별도로 기록한다. 최종 모델 비교에는 가능하면 여러 학습 seed를 사용하며, 가장 좋은 seed 하나만 골라 전체 구조의 성과로 보고하지 않는다.

교사 엔진은 오프라인 데이터 생성용이다. 실시간 대국에서 LC0나 Stockfish를 호출하는 경우 별도 hybrid 실험으로 명명하고 호출 시간·자원을 전부 포함한다. 주 평가의 독립 RoveZero 결과와 섞지 않는다.

## 11. 계측·정확성·실험 행렬

### 11.1 벤치마크 입력

독립 무작위 포지션만 사용하지 않는다. cold start, 부모→자식, 형제 후보 묶음, transposition 재방문, 캐시 eviction 후 재계산, 긴 게임 내 누적 갱신을 각각 측정한다. 실제 탐색 trace 재생은 원인 분석용이며, 최적화 후 탐색 분포가 달라질 수 있으므로 최종 실시간 대국을 다시 실행한다.

### 11.2 필수 계측

| 층위 | 기록할 값 |
|---|---|
| 모델 | 파라미터·활성 파라미터, MAC/FLOP 관례, 토큰·슬롯·반복 수, 정밀도 |
| 런타임 | 배치별 처리량, P50/P95/P99 지연, queue wait, H2D/D2H, kernel launch·동기화, 실제 메모리 |
| 캐시 | hit/miss, hit당 복원 비용, eviction, 공유율, 바이트/항목, 무효화 규모, 재사용 나이 |
| 탐색 | 고유 평가 수, 소비된 평가, 미사용 선행 평가, 취소, 중복 요청, 중요한 경로의 대기 |
| 품질 | policy 순위, WDL calibration, 교사 regret, 유일 방어 실패, fresh/warm 편차, 비정상 수치 |
| 대국 | WDL, pair 빈도, 득점률, 상대 Elo·CI, 시간 초과, 크래시, 표본·중단 규칙 |

NPS는 엔진별 정의가 다를 수 있다. 캐시 hit를 ‘새 신경망 계산’으로 세어 속도 향상을 부풀리지 않는다. 낮은 precision의 연산과 full 평가도 구분한다. 전력·에너지는 측정 가능할 때 부가 지표로 보고하되 주 Elo 규칙을 대체하지 않는다.

### 11.3 정확성 테스트

규칙 계층은 독립적인 참조 구현·공개 표준 포지션·perft 결과로 비교한다. 최적화 코드와 같은 갱신 함수를 호출하는 ‘참조’만 두지 않는다. 증분 특징은 별도의 전체 재계산과 비교하고, 여러 수의 make/unmake, 특수 수, 반복·카운터·차례 변경을 포함한다.

모델 계약은 합법 수 대응, promotion 구별, WDL 범위·관점, padding 독립성, precision별 허용 오차, deadline 종료를 검사한다. 캐시는 다른 모델·역사·정밀도·경로의 혼입, 충돌 처리, 수명 종료, 취소 후 결과를 검사한다. 검증기를 다시 검증하는 중복 체계보다 **실제 규칙·연산·출력 계약에 대한 독립 대조**를 우선한다.

### 11.4 최소 실험 행렬

| ID | 변경 | 고정할 것 | 1차 통과 조건 |
|---|---|---|---|
| X00 | 기준선 재현 | 모든 설정 | 정상 UCI·시간·pair 기록, 재실행 가능 |

## 12. 단계별 구현 순서와 종료 조건

| 단계 | 산출물 | 넘어갈 조건 |
|---|---|---|
| M0 평가 기반 | 잠긴 LC0 기준선, pair arena, manifest·PGN·통계 | 같은 시작 상태·시간·색 교대가 검증됨 |
| M1 실행 계측 | 기존 모델의 지연·메모리·shape·큐 profile | 병목과 측정 경계가 명확함 |
| M2 정확 재사용 | full/증분 두 경로와 캐시 타입 | 특수 수·긴 trace에서 계약 충족 |
| M3 소형 모델 비교 | square 기준선, 잠재/관계 후보, 동일 데이터 | 동일 학습 예산과 실제 지연 비교 가능 |
| M4 반복 보정 | fresh/warm, 다중 반복, 실패 복구 | tail error·경로 의존성·deadline 관리 |
| M5 실행 결합 | 양자화·큐·선행 평가 선택적 결합 | 각 요소가 독립적으로 설명 가능 |
| M6 대국 확인 | holdout 색 교대·동일 시간 대국, 전체 기록 | 사전 승격 규칙 충족 또는 불확정 명시 |

### 12.1 제안 저장소 역할 분리

`engine/`는 규칙·검색·UCI 경계를, `models/`는 인코더·본체·head를, `runtime/`은 평가 백엔드·캐시·큐를 맡는다. `training/`은 데이터·증류·자기대국, `arena/`는 대국·통계, `experiments/`는 manifest와 재현 가능한 설정, `tests/`는 독립 규칙·계약 대조를 맡는 구조를 제안한다. 실제 폴더와 언어는 포크/독립 구현 결정 후 조정한다.

초기 프로젝트의 차별점을 위해 검증된 이동 생성기·UCI 러너·통계 코드를 모두 새로 만들 필요는 없다. 반대로 평가 대상 엔진 내부가 자기 정확성의 유일한 판정자가 되면 안 된다. 재사용 범위와 독립 대조 범위를 구분한다.

### 12.2 즉시 중단·보류할 조건

의미 보존 경로에서 설명되지 않는 불일치, 잘못된 상태 캐시 공유, 자기 시간 밖의 신경망 계산, 다른 관점의 WDL 백업, 취소 작업의 중복 방문, 비교군의 잘못된 backend 설정이 발견되면 해당 실험의 Elo 해석을 중단하고 원인을 기록한다.

근사 경로의 작은 평균 오차만 좋고 드문 필패 전술이 늘면 보류한다. 커널은 빨라도 전체 엔진이 느리거나, 선행 평가 낭비가 실제 요청을 밀어내면 결합하지 않는다. ‘잠재 추론이 그럴듯하다’는 설명보다 동일 시간 결과를 우선한다.

### 13.3 이전 설명에서 명확히 바로잡은 해석

LC0는 단순 CNN 기준선이 아니다. 가상의 FFN=4d 계산은 실제 LC0 profile이 아니다. 압축률은 배속이 아니고, parameter sharing은 FLOPs 제거가 아니다. 평가 0은 불확실성이 아니며, speculative decoding의 정확성 보장은 체스 탐색으로 자동 이전되지 않는다.

첫 논의의 LLM 체스 성과는 연구 참고로 남겼지만 직접 언어 모델이 착수하는 경로를 목표로 삼지 않는다. 이전 응답에서 Fishtest 설명에 Marlin 주소가 연결되었던 부분은 분리했다. 통계 출처는 R53, Marlin 커널 출처는 R48이다.

모든 성능 우위는 출처의 원래 조건과 RoveZero의 실제 실험을 분리한다. 이번 문서에서 최종 채택·코드 구현·학습 성공·Elo 향상·저장소 생성이 완료되었다고 주장하는 항목은 없다.

## 14. CPU/GPU 적합성 평가 기준 — 전부 추론치

### 14.1 ‘GPU 엔진’은 전체 프로그램을 GPU에서 실행한다는 뜻이 아니다

본 프로젝트의 중심은 **GPU로 고비용 신경망 평가를 처리하는 LC0 계열의 연구 변형**이다. 합법 수 생성, 작은 메모리 조회, 트리 제어와 시간 관리는 CPU에 남을 수 있다. 실제 Ceres는 GPU 평가를 사용하면서 CPU의 SIMD 선택, 메모리 정렬·NUMA·prefetch와 배치 수집 중첩을 강조한다. LC0 변경 기록도 백엔드뿐 아니라 탐색 worker·잠금·DAG·메모리 이동을 함께 개선한다. [^R81] [^R89]

따라서 다음 세 축은 서로 대체할 수 없다.

| 평가 축 | 질문 | ‘낮음’의 의미 |
|---|---|---|
| CPU 적합성 | 작은 지연·분기·캐시·증분 갱신이 CPU 실행과 잘 맞는가? | 해당 형태를 CPU에 두는 것이 우선 후보가 아니라는 추론 |
| GPU 직접 적합성 | 일정한 작업을 충분히 묶어 병렬 연산·연속 메모리 접근을 활용할 수 있는가? | 원형 그대로 GPU에 옮기는 것이 불리할 수 있다는 추론 |
| GPU 중심 시스템 활용성 | CPU 보조로 실행하더라도 GPU 재평가·대기·잘못된 탐색을 줄일 수 있는가? | 최종 엔진에 이득을 줄 근거가 상대적으로 약하다는 추론 |

‘높음’은 구조상 유망, ‘조건부’는 배치·shape·메모리 상주·커널 지원에 민감, ‘낮음’은 현재 형태의 직접 이식이 불리할 것으로 본다는 뜻이다. **어느 등급도 실측 속도·Elo·확률을 나타내지 않는다.** ‘낮음~조건부’는 배치 재설계 등 특정 조건에서만 판단이 달라진다는 표시다. 개발·학습 전용 기법은 온라인 추론 축을 ‘해당 없음/오프라인’으로 표시한다.

### 14.2 추론의 전제와 판단을 뒤집을 수 있는 조건

일차 전제는 CPU와 분리된 메모리를 가진 단일 GPU, SIMD CPU, 고정된 모델, 실제 탐색에서 발생하는 불균일한 leaf 요청이다. NVIDIA 문서가 설명하는 메모리 접근 병합, host/device 전송, 작은 작업의 묶음 실행은 판단의 공학적 근거지만, 체스에서의 효과를 실측한 결과는 아니다. [^R83]

작은 배치와 큰 배치, discrete GPU와 통합 메모리 GPU, 소비자 장비와 서버 GPU는 결과가 다를 수 있다. 한 모델의 INT8 지원을 다른 모델·백엔드·행렬 크기로 일반화하지 않는다. GPU가 어떤 연산을 ‘지원한다’는 것과 해당 shape에서 빠르다는 것도 구분한다. Stormphrax가 같은 x86 기능 지원 여부와 실제 PEXT/PDEP 실행 효율을 구분하는 사례는 하드웨어별 검증의 필요성을 보여 준다. [^R79]

동일한 후보라도 실행 단위를 바꾸면 등급이 바뀔 수 있다. 예를 들어 한 노드의 accumulator add/sub는 CPU 우선으로 추정하지만, 많은 독립 노드의 delta를 합치고 특징·가중치를 GPU에 상주시킨 전용 커널은 다른 실험이다. 이때 부모 잠재 상태의 접근 패턴, GPU 메모리 사용, 갱신 목록 길이, 작은 배치의 대기까지 포함해야 한다.

### 14.3 검증할 비용 모델

개별 요청은 CPU 준비 → 큐 대기 → 전송 → GPU 계산 → 결과 반영이라는 의존 경로를 갖는다. 실제 파이프라인에서는 다른 요청의 단계가 겹칠 수 있으므로 각 단계의 시간을 단순 합산한 값을 전체 처리량으로 간주하지 않는다. **critical path 지연과 정상 상태 처리량을 모두 측정**한다.

주 계측은 수당 벽시계 시간, P50/P95/P99 평가 응답 시간, GPU·CPU 유휴 시간, 실제 소비된 고유 평가 수, 미사용·취소된 평가, 요청당 전송 바이트, 모델·캐시 상주량이다. GPU utilization이나 kernel FLOPs가 높아도 쓸모없는 형제 후보를 많이 계산하면 대국 성적이 나빠질 수 있다.

설계 단계에서의 판별 질문은 다음과 같다. 계산을 절약한 양이 launch·전송·동기화 비용을 넘는가? 좋은 후보를 찾기까지의 대기 시간이 줄었는가? cache hit는 full 평가와 같은 의미인가, 근사인가? 적게 본 후보에 유일한 방어 수가 숨어 있지 않은가? 최종 답은 2장의 동일 시간 대국으로 확인한다.

### 14.4 연구 경로와 유지 정책

| 경로 | 역할 | 제한과 비교 대상 |
|---|---|---|
| G — GPU 중심 | LC0식 평가·탐색을 유지하거나 GPU 친화적인 새 모델을 연구한다. | 주 목표. 원래 LC0와 같은 전체 장비·시간 한도에서 비교한다. |
| H — CPU 보조 혼합 | 작은 CPU 평가·전술 확인·history·cache 관리로 GPU를 돕는다. | CPU 사용량·검증 대기·모든 helper 비용을 자기 시계에 포함한다. |
| C — CPU 비교 연구 | NNUE·PVS·극저비트 등 CPU 친화적 후보를 독립적으로 연구한다. | 후보 보존·원인 분석용. 이것의 성과로 G의 GPU 아키텍처가 검증됐다고 주장하지 않는다. |
| O — 오프라인 | 데이터·학습·커널 튜닝·검증·실험 관리다. | 학습 GPU 적합성과 온라인 추론 적합성을 섞지 않는다. |

CPU-only 모델이 같은 전체 장비 허용 조건에서 GPU LC0를 이기면 유효한 시스템 결과다. 그러나 GPU 아키텍처 개선 결과는 아니다. 필요하면 CPU-only 동일 조건에서 Stockfish·Reckless 등과 별도로 대국하여 해석을 보강한다. 서로 다른 트랙·시간·하드웨어 결과를 하나의 Elo로 합치지 않는다.

**보존 정책:** 모든 카드의 ID와 출처를 유지한다. 기각·보류·부정적 결과도 지우지 않고 이유·장비·측정 범위를 기록한다. GPU 적합성이 낮은 알고리즘은 H/C/O 경로에 남길 수 있으며, 높은 알고리즘도 실측에서 손해면 배치와 우선순위를 바꾼다.

공개 코드가 있다는 사실은 해당 알고리즘의 최초 발명자라는 뜻이 아니다. 여러 엔진이 비슷한 기법을 공유하며, 릴리스 전체의 Elo 향상은 그 안의 한 변경 효과를 식별하지 못한다. 아래 소스는 **정적 열람**한 것이고 전체 저장소를 검증·실행한 결과가 아니다.

### 15.3 이번 조사에서 수정된 우선순위

B01의 증분 계산은 유망하지만 GPU 중심 프로젝트의 자동 1순위로 두지 않는다. **먼저 LC0 기존 GPU 경로를 계측하고, CPU 병목·GPU 대기·메모리 상주 여부를 본 뒤** 증분 설계를 선택한다. 반면 threat/pawn-pair 같은 관계 입력의 원리는 CPU NNUE에만 종속되지 않으므로, GPU Transformer의 relation bias·보조 입력·작은 head로 바꾸어 독립 실험할 가치가 있다.

고정된 동일 탐색 트리에 적용하는 기본 alpha-beta의 정확한 가지치기와, LMR·null-move·futility 같은 선택적 휴리스틱을 구분한다. 후자의 감축·생략은 필요한 수를 놓칠 위험을 감수하는 기법이다. CPU 엔진의 튜닝 상수·centipawn margin을 WDL 기반 PUCT에 옮기는 것은 단순 구현 이식이 아니라 새 탐색 알고리즘이다. 초기에 후보 순서·추가 반복의 신호로만 사용하고, 영구 제외는 별도 고위험 실험으로 둔다.

### 15.4 채택 사례뿐 아니라 제거 사례도 본다

2026-09-05 Stockfish 19 공식 발표는 중복 threat 특징을 줄이고 pawn-pair 특징을 도입한 SFNNv16, 양자화 인지 학습(QAT), Leela 네트워크로 재평가한 학습 자료를 설명한다. 또한 Stockfish 16.1에서 도입했던 작은 보조 네트워크를 제거했다고 보고한다. 이 내용은 **저자 발표**이며, 이번 작업에서 개별 변경의 대국 효과를 재현하지 않았다. [^R93]

RoveZero에서는 F09/F10의 관계 입력과 F27의 증류에 근거를 보강하되, F26의 이중 평가기를 자동 채택하지 않는다. 작은 모델이 놓치는 전술·그 모델을 잘못 선택하는 gate·두 평가 척도의 불일치가 전체 이득을 없앨 수 있다는 반대 가설을 등록한다. 반대로 이 Stockfish 변경이 CPU+GPU 혼합 평가기를 전부 반박하는 것도 아니다. 각 모델 크기·선택 정책·시간·하드웨어에서 실험한다.

## 16. 추가 후보 F — 현대 엔진의 핵심·세부 알고리즘

각 카드의 출처는 기존 구현 또는 원리의 근거다. ‘RoveZero 적용’은 달리 명시하지 않는 한 새 가설이며, **CPU/GPU 등급은 전부 추론치·미측정**이다. 초기 순서는 17장에 정리했다. 기존 A~E 카드와의 연결을 적어 중복 효과를 이중 계산하지 않게 했다.

### F01. PVS·반복 심화·aspiration window

**원리·확인 근거.** Reckless의 검색은 PV/non-PV를 구분하고 좁은 창의 탐색과 재탐색을 사용하며, 반복 탐색의 aspiration window를 조절한다. [^R70]

**RoveZero 적용·한계.** C 경로의 CPU 기준선, 또는 H 경로의 작은 전술 확인기에 사용한다. 이전 결과로 후속 탐색을 좁힌다는 아이디어는 예산 제어에 차용할 수 있지만, PUCT에 alpha/beta 창을 덧붙이는 것으로 동일 알고리즘이 되지 않는다. 재탐색은 강한 수순 의존성을 만든다.

**하드웨어 적합성 — 추론치·미측정.** CPU **높음** / GPU 직접 **낮음** / GPU 시스템 **조건부**. 배치: H/C의 CPU. 최소 실험은 고정 작은 평가기로 PVS 비용·재탐색률을 기록하고, GPU 호출이 한 노드씩 직렬화되는지 확인한다. 연결: C01·C07.

### F02. Null-move·reverse futility·razoring·ProbCut

**원리·확인 근거.** Reckless의 소스에는 가상 패스 탐색, 정적 평가 margin, 얕은 전술 탐색으로 깊은 탐색을 생략하는 여러 경로와 일부 검증 검색이 있다. [^R70]

**RoveZero 적용·한계.** CPU verifier의 제한적 선택 탐색 또는 ‘더 계산할 필요성’의 입력으로 연구한다. 이 결과는 증명된 게임 가치가 아니며, zugzwang·체크·희생·낮은 물질 상태 등에서 실패할 수 있다. null move를 실제 합법 수나 자기대국 데이터의 이동으로 기록하지 않는다. LC0 후보의 영구 pruning은 별도 가설이다.

**하드웨어 적합성 — 추론치·미측정.** CPU **높음** / GPU 직접 **낮음** / GPU 시스템 **조건부**. 배치: H/C host. 최소 실험은 gate만 켠 버전과 실제 생략 버전을 나누고 유일 방어·zugzwang 회귀 및 같은 시간 대국을 비교한다. 연결: C01·C07.

### F03. LMR·LMP·history/SEE 기반 선택성

**원리·확인 근거.** Reckless는 늦게 등장하는 수의 깊이를 줄이고, history·위협·평가 차이에 따라 감축량·생략을 조절하며, 필요하면 더 깊게 재탐색한다. [^R70]

**RoveZero 적용·한계.** GPU 반복 평가에서 뒤쪽 후보에 작은 초기 예산을 주는 아이디어로 바꿀 수 있다. 순서가 낮다는 이유로 합법 후보를 영구 삭제하거나 reduced 결과를 full-depth 결과로 캐시하지 않는다. LMR과 LMP는 ‘덜 보기’와 ‘안 보기’로 구분한다.

**하드웨어 적합성 — 추론치·미측정.** CPU **높음** / GPU 직접 **낮음~조건부** / GPU 시스템 **조건부**. 배치: CPU 결정, GPU는 고정 예산별 큐. 최소 실험은 작은 예산에서 놓친 후보가 재진입할 수 있는지와 재탐색·배치 분할 비용을 본다. 연결: C02·C08.

### F04. Singular extension·유일 후보와 대안 반박

**원리·확인 근거.** Reckless의 singular 검색은 유력한 TT 수를 제외한 대안을 탐색해 상대적 유일성을 추정하고 깊이를 늘리거나 다른 처리를 한다. [^R70]

**RoveZero 적용·한계.** 유력 후보를 더 보는 대신 ‘그 수가 유일한지’를 확인하는 별도 계산 예산으로 차용한다. GPU에서는 대안 묶음 평가나 candidate regret head가 가능하다. 높은 policy 하나만으로 유일성을 확정하지 않으며, 얕은 대안 탐색은 반증 실패일 뿐 증명이 아니다.

**하드웨어 적합성 — 추론치·미측정.** CPU **높음** / GPU 직접 **조건부** / GPU 시스템 **조건부**. 최소 실험은 유일 방어·희생군에서 대안 검증 비용 대비 실제 착수 개선을 측정한다. 연결: A06·C01·E01.

### F05. Quiescence·SEE·값싼 전술 확인

**원리·확인 근거.** Reckless·Obsidian에는 정규 검색과 qsearch를 분리하는 경로가 있고, Reckless는 SEE를 후보 필터에 사용한다. [^R70] [^R78] [^R88]

**RoveZero 적용·한계.** 불안정한 leaf에서 제한된 CPU 전술 확인을 수행하거나 그 필요성을 예측한다. SEE는 교환의 국소 추정이며 장기 희생·체크메이트의 완전한 판정기가 아니다. qsearch도 전술 종료 범위와 가지치기에 따라 근사다. 모든 GPU leaf에 무조건 호출하면 CPU가 병목이 될 수 있다.

**하드웨어 적합성 — 추론치·미측정.** CPU **높음** / GPU 직접 **낮음~조건부** / GPU 시스템 **조건부**. H 우선. 최소 실험은 root/불안정 leaf 한정과 전 leaf 호출을 비교하고 helper 사용 시간과 전술 누락을 기록한다. 연결: C05·F26.

### F06. Quiet·capture·continuation·pawn·countermove history

**원리·확인 근거.** Viridithas·Obsidian·Reckless의 선택 소스에는 이전 탐색의 성공·실패를 수·기물·폰 구조·이전 수·위협 문맥에 연결하는 history 계열이 있다. [^R70] [^R75] [^R78]

**RoveZero 적용·한계.** 작은 host 테이블을 후보 우선순위나 초기 예산의 보조 신호로 사용한다. 학습 policy와 섞을 때 정규화·감쇠·새 게임 초기화를 명시하고, history bonus를 신경망 logit 또는 실제 방문 횟수처럼 해석하지 않는다. 알파베타 cutoff 성공과 PUCT의 좋은 착수는 같은 라벨이 아니다.

**하드웨어 적합성 — 추론치·미측정.** CPU **높음** / GPU 직접 **낮음** / GPU 시스템 **조건부~높음**. 최소 실험은 history만/정책만/혼합을 나누고 lookup 비용·탐색 쏠림·게임 간 누출을 본다. 연결: C01·F21.

### F07. Correction history·온라인 잔차 보정

**원리·확인 근거.** 여러 엔진은 원시 정적 평가와 검색 결과의 차이를 폰·기물·이전 수 문맥별로 학습해 보정한다. Reckless는 raw_eval과 corrected eval을 구별하고, Viridithas·Obsidian에도 여러 correction 계열이 있다. [^R70] [^R75] [^R78]

**RoveZero 적용·한계.** 원시 WDL을 덮어쓰지 않고 작은 별도 residual 또는 추가 계산 gate를 연구한다. centipawn 보정값을 WDL에 바로 더하지 않는다. 탐색 중 바뀌는 보정은 비정상성·자기확증 편향을 만들므로 버전·학습 대상·감쇠·초기화를 기록한다. bound 결과를 exact 교사 라벨로 삼지 않는다.

**하드웨어 적합성 — 추론치·미측정.** CPU **높음** / GPU 직접 **낮음** / GPU 시스템 **조건부**. 최소 실험은 raw cache와 보정 결과의 분리, 보정 전후 calibration·최선수 변화·같은 시간 대국이다. 연결: E02·C01.

### F08. Improving·hindsight reduction·계산 후 재판단

**원리·확인 근거.** Reckless는 이전 ply와 평가 차이를 이용한 improving 신호와, 앞서 줄인 깊이를 자식의 결과를 보고 조정하는 hindsight 처리를 구현한다. [^R70]

**RoveZero 적용·한계.** 잠재 반복·저정밀 평가의 다음 단계를 결정하는 저비용 신호로 차용한다. 단순히 좋아 보이는 상태와 오판 가능성이 높은 상태를 구분해야 한다. 여러 head의 출력 관점·50수 보정·correction 변경이 평가 차이에 섞이는 것을 통제한다.

**하드웨어 적합성 — 추론치·미측정.** CPU **높음** / GPU 직접 **낮음** / GPU 시스템 **조건부~높음**. 최소 실험은 한 번 정한 예산과 결과를 보고 재배분하는 예산을 비교하고 취소·재진입 비용을 포함한다. 연결: C01~C03.

### F09. Threat inputs·기물 간 공격/방어 관계

**원리·확인 근거.** Reckless와 PlentyChess는 기물 간 상호작용을 평가 입력에 넣고, Viridithas에는 threat 변경분 갱신 코드가 있다. PlentyChess의 릴리스는 관계 입력으로 평가가 느려졌어도 전체 엔진이 강해졌다고 보고한다. [^R71] [^R72] [^R74] [^R76]

**RoveZero 적용·한계.** NNUE의 큰 sparse index를 그대로 GPU에 옮기기보다 relation embedding·attention bias·보조 head·CPU 생성 bitmask를 비교한다. ‘위협’이 합법 포획인지 기하학적 공격인지, 핀·왕·아군 방어를 어떻게 정의하는지 명시한다. 기존 GAB와 정보가 중복될 수 있다.

**하드웨어 적합성 — 추론치·미측정.** CPU **높음** / GPU 직접 **조건부** / GPU 시스템 **높음**. 최소 실험은 기존 GPU 기준선에 관계 입력 하나만 추가하고 생성·전송·추론 시간까지 포함한다. 연결: A01~A03·B01.

### F10. Pawn-pair 특징·저비용 구조 상호작용

**원리·확인 근거.** PlentyChess snapshot은 pawn-pair feature 공간과 추가/제거 delta 인터페이스, 파일 주변의 pair mask를 정의한다. 일반 기물 threat와 구분된 특징이다. Stockfish 19 공식 발표도 pawn-pair 특징 도입을 설명한다. [^R73] [^R93]

**RoveZero 적용·한계.** 폰 구조의 쌍 관계를 작은 학습 입력이나 캐시로 제공한다. 모든 기물 쌍을 펼치는 대신 구조적으로 제한된 관계부터 비교한다. 폰 이동·포획·승격 때의 무효화, 양쪽 색과 좌표의 의미를 검사한다. ‘폰은 느리게 변한다’는 관찰만으로 항상 hit가 높다고 가정하지 않는다.

**하드웨어 적합성 — 추론치·미측정.** CPU **높음** / GPU 직접 **낮음~조건부** / GPU 시스템 **조건부**. CPU 생성+GPU 입력을 우선하고 batch pair gather와 비교한다. 연결: A03·A04·B02.

### F11. Lazy accumulator·Finny cache·refresh와 delta 선택

**원리·확인 근거.** Reckless는 평가가 필요할 때 accumulator를 갱신하며 일부 왕 위치 변화에서 refresh한다. Alexandria·Obsidian은 FinnyTable 형태의 중간 특징 캐시를 둔다. [^R71] [^R77] [^R78]

**RoveZero 적용·한계.** 특징이 필요한 시점까지 갱신을 미루고, 유사한 캐시 상태와의 delta가 새 계산보다 쌀 때 사용한다. Finny cache는 완전한 평가값 TT가 아니다. GPU에서는 부모별 무작위 가중치 읽기·다층 state 상주량·refresh 빈도가 비용을 만들므로 CPU 이득을 그대로 예상하지 않는다.

**하드웨어 적합성 — 추론치·미측정.** CPU **높음** / GPU 직접 **낮음~조건부** / GPU 시스템 **조건부**. 최소 실험은 full/즉시 갱신/lazy/캐시 refresh 네 가지와 특수 수·긴 make/unmake trace다. 연결: B01·B08.

### F12. King bucket·미러링·재료량별 출력 head

**원리·확인 근거.** Reckless와 Alexandria는 왕 위치의 입력 bucket, 좌표 변환, 기물 수에 따른 출력 bucket 계열을 사용한다. [^R71] [^R77]

**RoveZero 적용·한계.** 작은 shared trunk와 소수 조건부 head의 전문화 후보로 사용한다. 미러링을 실제 게임 상태 변환과 혼동하지 않고 입력 변환과 move 출력 역변환을 함께 정의한다. 왕이 경계를 넘을 때 대규모 cache 무효화가 생길 수 있다. batch를 head별로 나누면 작은 행렬이 늘어난다.

**하드웨어 적합성 — 추론치·미측정.** CPU **높음** / GPU 직접 **조건부** / GPU 시스템 **조건부**. 최소 실험은 단일 head와 grouped head의 같은 시간 대국, 경계 포지션의 평가 불연속이다. 연결: A07·E06.

### F13. 활성 인덱스·혼합 정밀도·작은 후단 신경망

**원리·확인 근거.** Reckless에는 nonzero 인덱스를 찾는 표와 sparse 첫 후단 경로가 있고, Alexandria에는 int16 FT·int8 첫 층·float 후단 및 dual-activation 구조가 정의돼 있다. [^R71] [^R77]

**RoveZero 적용·한계.** 모든 층을 같은 precision으로 강제하지 않고, 민감 head·누산과 큰 가중치 저장을 분리한다. CPU의 작은 활성 인덱스 loop와 GPU의 block/tensor sparsity는 다르다. activation·scale 변경은 모델·학습 계약 변화이며 단순 bit packing과 구별한다.

**하드웨어 적합성 — 추론치·미측정.** CPU **높음** / GPU 직접 **조건부** / GPU 시스템 **조건부**. 최소 실험은 dense 저차원 기준, sparse 실행, precision 조합의 P99 오류와 실측 지연이다. 연결: D06~D09.

### F14. TT bound·원시 평가 캐시·MCTS 통계 분리

**원리·확인 근거.** Reckless는 TT의 검색 깊이·bound·검색 점수·raw eval을 다르게 취급한다. LC0/Ceres는 신경망 평가 재사용과 트리 탐색 통계의 별도 구조를 제공한다. [^R70] [^R80] [^R81]

**RoveZero 적용·한계.** 정확 상태 식별, 네트워크 출력, 선택적 검색 결과, edge별 방문·in-flight를 다른 계약으로 둔다. 알파베타의 lower/upper 표기는 그 검색 전제에 따른 정보이지 근사 pruning을 포함한 모든 상황의 게임이론적 증명이 아니다. transposition eval hit만으로 새 방문을 만들지 않는다.

**하드웨어 적합성 — 추론치·미측정.** CPU **높음** / GPU 직접 **낮음~조건부** / GPU 시스템 **높음**. 최소 실험은 history·모델·정밀도·경로 혼입, 동시 hit와 취소·중복 backup이다. 연결: B07·B08·4.4절.

### F15. 반복·50수 상태·mate 거리의 선행 처리

**원리·확인 근거.** Reckless 소스는 반복 가능성, 무승부, mate distance, halfmove 정보를 검색과 TT 접근에 반영한다. Obsidian도 반복과 평가 보정을 구분한다. [^R70] [^R78]

**RoveZero 적용·한계.** 확실한 종료·규칙 판정을 신경망 호출 전에 처리해 GPU 작업을 줄인다. 휴리스틱 draw score나 알파베타 mate 창 조절과 정확한 종료 판정은 분리한다. FEN의 보드가 같아도 반복 이력·앙파상·캐슬링·카운터가 다르면 같은 캐시 항목으로 합치지 않는다.

**하드웨어 적합성 — 추론치·미측정.** CPU **높음** / GPU 직접 **낮음~조건부** / GPU 시스템 **높음**. 최소 실험은 동일 보드·다른 이력의 대조, 실제 종료와 draw 추정의 구분, 제거된 GPU 호출 수다. 연결: B08·F14.

### F16. Bitboard·magic/PEXT·단계별 수 생성

**원리·확인 근거.** Reckless의 board/movegen·SEE 및 magic 관련 파일과 Stormphrax의 ISA별 경로는 비신경망 기본 연산의 비용을 낮추는 비교 자료다. Stormphrax는 PEXT/PDEP의 실제 효율이 CPU 세대에 따라 다름을 명시한다. [^R79] [^R88]

**RoveZero 적용·한계.** CPU movegen·위협 생성이 GPU를 굶기면 먼저 최적화한다. ISA 이름을 GPU 명령에 일대일 대응시키지 않는다. 단계적 수 생성으로 아직 필요하지 않은 수의 정렬 비용을 미룰 수 있지만, 신경망 출력의 합법 수 계약은 유지해야 한다.

**하드웨어 적합성 — 추론치·미측정.** CPU **높음** / GPU 직접 **조건부** / GPU 시스템 **높음**. GPU에서는 많은 보드의 일괄 생성만 별도 연구한다. 최소 실험은 독립 perft·합법성 대조와 CPU starvation 계측이다. 연결: F30.

### F17. Cache-line·작은 node/TT 레이아웃·prefetch

**원리·확인 근거.** Stormphrax는 정렬된 작은 TT cluster와 thread data를 정의한다. Ceres는 작은 node index·고정 크기 정렬 노드와 prefetch 등을 설명하고, Reckless는 검색 중 TT prefetch를 사용한다. [^R70] [^R81] [^R87]

**RoveZero 적용·한계.** hot/cold 필드와 metadata를 분리하고 평가 요청·트리의 working set을 줄인다. CPU에서 유리한 AoS가 GPU coalescing에 유리하다는 보장은 없으므로 SoA 또는 혼합 레이아웃도 비교한다. 작은 index에는 overflow·수명·generation 검사가 필요하다.

**하드웨어 적합성 — 추론치·미측정.** CPU **높음** / GPU 직접 **조건부** / GPU 시스템 **높음**. 최소 실험은 cache miss·RSS/VRAM·lock wait·실제 leaf 공급 지연과 잘못된 handle 재사용이다. 연결: B08·D01.

### F18. 병렬 탐색 worker·NUMA·공유 정보

**원리·확인 근거.** Reckless는 다중 worker와 NUMA 개선을 보고하고, Stormphrax와 Ceres도 NUMA·cache-line·메모리 지역성을 다룬다. [^R72] [^R79] [^R81]

**RoveZero 적용·한계.** CPU 알파베타의 Lazy-SMP 계열 아이디어는 C 경로 비교 후보로 보존하고, G에서는 shared tree와 batch gather를 우선한다. 여러 탐색기가 같은 GPU 평가를 중복 요청하는 구조를 무조건 병렬화 이득으로 보지 않는다. 고전 구현의 volatile 표기를 atomic·메모리 순서 보장으로 오해하지 않는다.

**하드웨어 적합성 — 추론치·미측정.** CPU **높음** / GPU 직접 **낮음** / GPU 시스템 **높음(병목 시)**. 최소 실험은 1/여러 worker의 유효 평가·중복·GPU 유휴·NUMA 원격 접근이다. 단일 소켓에서는 NUMA 이득이 없을 수 있다. 연결: D03.

### F19. 최선수·평가·PV 안정성 기반 시간 관리

**원리·확인 근거.** Reckless의 시간 배분은 노드 분포·PV/평가 안정성·점수 변화·최선수 변경을 결합한다. LC0도 검색 통계와 시간 사용 힌트를 관리한다. [^R70] [^R80]

**RoveZero 적용·한계.** 네트워크 entropy 하나 대신 실제 의사결정 안정성과 남은 시계를 고려한다. 전체 게임의 equal clock 실험과 equal movetime 실험을 분리하면 이 효과를 식별할 수 있다. 복잡한 상태라는 이유로 hard deadline을 넘기지 않으며, 마지막 유효 착수를 유지한다.

**하드웨어 적합성 — 추론치·미측정.** CPU **높음** / GPU 직접 **낮음** / GPU 시스템 **높음**. 최소 실험은 동일 evaluator에서 시간 관리자만 교체하고 시간초과·장기 대국 득점률을 함께 기록한다. 연결: C01·2.2절.

### F20. Syzygy·정확한 endgame 정보의 선택적 probe

**원리·확인 근거.** Reckless에는 tablebase probe·결과 bound·TT 반영 경로가 있고, Stormphrax는 root-only·깊이·기물 수 제한 옵션을 제공한다. [^R70] [^R79]

**RoveZero 적용·한계.** 정확한 조건에서 GPU 평가를 대체하거나 검증한다. WDL/DTZ, 50수 규칙, probe 가능 상태와 실패를 구분하고 파일 접근·디스크 지연을 시계에 포함한다. 비교군과 동일한 파일·허용 범위 또는 양쪽 비활성 정책을 적용한다.

**하드웨어 적합성 — 추론치·미측정.** CPU **높음** / GPU 직접 **낮음** / GPU 시스템 **높음(적용 국면)**. 최소 실험은 root-only/내부 probe의 지연·hit·동일 규칙 판정이며, GPU 직접 적합성이 낮아도 유지한다. 연결: F15·2.7절.

### F21. FPU·PUCT·in-flight·dual CPUCT와 배치 선택

**원리·확인 근거.** LC0는 FPU·PUCT와 in-flight 상태를 사용한다. Ceres는 배치별 두 CPUCT 수준, relative virtual loss, AVX 기반 선택, 수집/평가 중첩을 설명한다. [^R80] [^R81] [^R89]

**RoveZero 적용·한계.** 같은 leaf에 몰리는 요청을 줄이면서 중요한 경로가 과도하게 밀리지 않게 한다. GPU utilization만 최대화하지 않는다. virtual loss/in-flight는 실행 중 예약이지 실제 패배나 완료 방문이 아니며 취소 시 정확히 해제한다. 기존 LC0 구현을 기준선에 포함한다.

**하드웨어 적합성 — 추론치·미측정.** CPU **높음** / GPU 직접 **조건부** / GPU 시스템 **높음**. CPU SIMD 선택+GPU batch가 우선. 최소 실험은 충돌률·batch fill·stale 결과·root regret·동일 시간 대국이다. 연결: D03·C06.

### F22. DAG·transposition·virtual subtree

**원리·확인 근거.** LC0는 DAG 탐색 경로를 포함하고, Ceres는 기존 트리 안의 transposition 평가 재사용과 virtual subtree를 설명한다. [^R81] [^R89]

**RoveZero 적용·한계.** 같은 실제 신경망 입력은 평가를 재사용하되 다른 부모 edge의 방문·가치 backup을 혼합하지 않는다. 이력·반복·근사 warm-state가 다르면 같은 board hash만으로 합치지 않는다. 트리 단순 공유와 완전한 DAG 검색은 다른 변경이므로 분리한다.

**하드웨어 적합성 — 추론치·미측정.** CPU **높음** / GPU 직접 **조건부** / GPU 시스템 **높음**. 최소 실험은 정확 eval dedup부터 시작하고, 이후 DAG 수명·cycle/반복·GC·동시 backup을 검사한다. 연결: B08·C03·F14.

### F23. Sibling blending·다른 경로에서 얻은 형제 정보

**원리·확인 근거.** Ceres의 sibling blending은 현재 subtree에서 미평가인 형제라도 다른 경로에서 transposition으로 평가됐으면 그 정보를 활용하는 방식으로 설명된다. [^R81]

**RoveZero 적용·한계.** A06의 ‘부모 인코더로 모든 형제를 새로 예측’하는 것과 다르다. 이미 존재하는 평가를 찾아 초기 추정에 반영하는 경로부터 비교한다. sibling의 평균을 자체 방문 결과로 둔갑시키거나 여러 번 backup하지 않는다. 실제 입력 이력이 다르면 재사용 자격이 없을 수 있다.

**하드웨어 적합성 — 추론치·미측정.** CPU **높음** / GPU 직접 **낮음~조건부** / GPU 시스템 **조건부**. 최소 실험은 사용 가능한 기존 정보의 비율, 혼합 weight별 편향, 탐색 효율과 대국이다. 연결: A06·B08.

### F24. 불확실성 boosting·Q/N 선택 규칙

**원리·확인 근거.** Ceres는 backup 평가의 변동성을 탐색 유인으로 쓰고, 상황에 따라 방문 수 N보다 subtree 평가 Q 중심으로 최선수를 고르는 설계를 설명한다. [^R81]

**RoveZero 적용·한계.** 추가 계산 가치 예측의 단순 비교 기준으로 사용한다. 변동성·WDL 무승부 확률·인식 불확실성을 혼동하지 않으며, 적은 방문의 낙관적인 Q가 불안정할 수 있다. 최종 move rule만 바꿀 때도 policy/검색 변경과 분리한다.

**하드웨어 적합성 — 추론치·미측정.** CPU **높음** / GPU 직접 **낮음~조건부** / GPU 시스템 **조건부~높음**. 최소 실험은 N 기반/Q 기반/안정성 조건부 선택의 낮은·높은 시간 예산 비교다. 연결: C01·C07·E02.

### F25. Gumbel AlphaZero·sequential halving

**원리·확인 근거.** 원 논문은 적은 simulation에서의 policy improvement 문제를 다루며, 중복 없는 후보 표본과 예산 배분을 활용한 Gumbel AlphaZero/MuZero를 제시한다. [^R82]

**RoveZero 적용·한계.** 고정된 후보군에 묶음 예산을 주고 단계적으로 줄이는 root 실험을 만든다. 기존 LC0 가중치에 맞춰 PUCT와 같은 시간에 비교한다. 학습 때의 exploration과 평가 때의 선택을 구별하고 난수 정책을 사전에 고정한다. 적은 budget의 원문 결과를 긴 시간의 최신 LC0 Elo로 전용하지 않는다.

**하드웨어 적합성 — 추론치·미측정.** CPU **높음** / GPU 직접 **조건부** / GPU 시스템 **높음(묶음 실행 가설)**. 최소 실험은 좁은/넓은 후보군·재진입 여부·stage wait를 포함한다. 연결: C07·A06.

### F26. 작은 CPU 평가기와 큰 GPU 평가기의 이중 경로

**원리·확인 근거.** 저렴한 NNUE 평가·전술 탐색과 GPU neural search는 각각 기존 엔진의 근거가 있다. 여기서 제안하는 호출 정책·결합 구조 자체의 강도는 검증되지 않았다. Stockfish 19는 작은 보조 네트워크를 제거했다고 발표했으므로, 작은/큰 평가기 결합에 대한 반대 사례도 함께 남긴다. 이는 CPU+GPU 혼합 구조 전체의 반증은 아니다. [^R03] [^R71] [^R81] [^R93]

**RoveZero 적용·한계.** CPU는 initial priority·전술 경고·긴급 자체 fallback, GPU는 정밀 policy/WDL을 맡는 후보를 만든다. 두 평가의 척도·편향을 calibration하고 모델별 cache와 provenance를 분리한다. GPU 요청을 무조건 CPU 확인 뒤에만 보내 직렬 병목을 만들지 않는다. 타 엔진 프로세스 호출은 별도 composite 실험으로 명시한다.

**하드웨어 적합성 — 추론치·미측정.** CPU **높음** / GPU 직접 **높음(큰 평가만)** / GPU 시스템 **조건부**. 최소 실험은 gate 비용·GPU 절감·실수 복구·양쪽 메모리·전체 시계 비용이다. 연결: C05~C07·F05.

### F27. Self-distillation·feature factorization·NNUE 학습 분리

**원리·확인 근거.** PlentyChess는 self-distillation 사용을 설명한다. Alexandria는 factoriser 필드가 있는 학습/네트워크 구조를 정의한다. Bullet은 NNUE 중심 GPU 학습 도구를 제공한다. Stockfish 19는 QAT와 Leela로 재평가한 학습 자료를 설명한다. 학습 교사의 하드웨어와 추론 엔진의 하드웨어는 같을 필요가 없다. [^R77] [^R85] [^R86] [^R93]

**RoveZero 적용·한계.** 관계·bucket 특징의 데이터 희소성을 학습 구조로 보완하고, 추론 때 가능한 정적 병합을 검토한다. source의 필드 존재만으로 현재 exporter가 어떤 병합을 하는지 단정하지 않는다. Bullet을 Transformer trainer의 즉시 대체재로 취급하지 않고 모델별 지원을 확인한다.

**하드웨어 적합성 — 추론치·미측정.** CPU/GPU 온라인 **해당 없음** / GPU 학습 **높음~조건부** / GPU 시스템 **조건부**. 최소 실험은 같은 데이터 생성+학습 총비용과 export 전후 일치다. 연결: E01·E03·D04.

### F28. SPRT·분산 실험·소수 파라미터 튜닝

**원리·확인 근거.** OpenBench는 분산 SPRT 기반 체스 엔진 실험을 제공하고, Fishtest는 paired 게임 통계·검정과 튜닝 방법을 설명한다. [^R53] [^R84] [^R90]

**RoveZero 적용·한계.** PUCT·cache policy·gate threshold·batch timeout 등 작은 파라미터를 controlled tuning 후보로 둔다. SPSA 같은 동시 perturbation은 GPU 런타임 알고리즘이 아니라 오프라인 실험 절차다. holdout·같은 장비·시간 조건·검정 종료 규칙을 잠그고 최종 확인 세트로 튜닝하지 않는다.

**하드웨어 적합성 — 추론치·미측정.** CPU/GPU 온라인 **해당 없음** / 개발 활용 **높음**. 최소 실험은 parameter 변경을 제외한 조건 재현, paired PGN 감사, 실패·불확정 보존이다. 연결: E12·2장.

### F29. PGO·ISA별 빌드·CPU 제어 경로 최적화

**원리·확인 근거.** Reckless는 PGO 빌드를 제공하고, PlentyChess·Stormphrax는 대상 CPU별 빌드 및 프로파일링 경로를 설명한다. [^R79] [^R86] [^R92]

**RoveZero 적용·한계.** host movegen·tree walk·cache 경로를 실제 탐색 trace로 최적화한다. CPU PGO가 GPU kernel을 자동 최적화하는 것은 아니다. 테스트 opening만으로 profile을 만들지 않으며 배포 장비가 지원하지 않는 명령을 사용하지 않는다. baseline도 정상 최적화 빌드여야 한다.

**하드웨어 적합성 — 추론치·미측정.** CPU 산출물 **높음** / GPU 직접 **해당 없음** / GPU 시스템 **높음(host 병목 시)**. 최소 실험은 non-PGO/PGO와 장비별 build의 동일 모델·시간 비교다. 연결: D01·D10.

### F30. GPU 일괄 상태 처리·stream compaction·상주 frontier

**원리·확인 근거.** CPU 엔진의 movegen/bitboard와 GPU의 coalescing·batch 처리·wavefront 원리를 결합하는 제안이다. 위 신흥 엔진들이 이 GPU 구조를 구현했다는 주장이 아니다. [^R33] [^R83] [^R88]

**RoveZero 적용·한계.** 많은 leaf의 보드를 GPU에 유지하고 합법성/입력 생성/종료 mask를 일괄 처리한 뒤 유효 항목만 모아 평가한다. 재귀 PVS 전체를 커널로 옮기는 것과 구분한다. board state·이력·특수 수·compaction index·메모리 크기 계약이 추가된다. CPU 입력 생성이 이미 충분히 빠르면 우선순위가 낮다.

**하드웨어 적합성 — 추론치·미측정.** CPU 원형 **높음** / GPU 재설계 **조건부** / GPU 시스템 **조건부**. 최소 실험은 독립 CPU 규칙 참조와 일괄 GPU 결과 대조, 배치 크기별 전송 절감·발산·전체 지연이다. 연결: D03·F16.

### 17.2 GPU 적합성 가설을 실제로 바꿀 측정

microbenchmark는 제안상 batch 1/4/16/64/256을 사용하되, 메모리·장비 한도를 넘으면 생략 이유를 기록한다. 이는 강제 표준이 아니라 작은 latency 영역과 묶음 처리 영역을 함께 보기 위한 시작점이다. 실제 탐색 batch 분포·deadline 정책은 별도로 측정한다.

각 후보마다 CPU-only, GPU-direct, CPU+GPU 배치의 가능한 변형을 비교한다. GPU에는 가중치·특징 상주 여부와 H2D/D2H 바이트, CPU에는 SIMD·스레드·NUMA·캐시 조건을 적는다. warm-cache/cold-cache와 왕 bucket 경계·많은 threat delta·특수 수·long trace를 나눈다. 큰 배치에서만 이득인 기법을 저시간 대국에도 유리하다고 일반화하지 않는다.

수치 결과가 비슷한 모델은 같은 평가 횟수 비교로 표현력 영향을 보고, **최종 승격은 2장의 같은 벽시계 대국**으로 판정한다. GPU head 추가나 history 보정으로 탐색 순서가 바뀌면 단순 실행 최적화가 아니라 A/S 변경으로 기록한다. CPU에 남긴 기술의 성과도 GPU 중심 시스템 개선으로 보고할 수 있지만 ‘GPU 직접 가속’이라고 표기하지 않는다.

### 17.3 기존 대국 계약에 추가할 사항

주 평가는 여전히 **같은 시작 포지션에서 엔진의 흑백을 바꾼 두 판**, **LC0와 같은 기본 시계·증분·장비 한도**, **승 1/무 0.5/패 0의 득점률**, **pair 상관을 반영한 통계**다. 2장의 규칙을 유지한다. normalized Elo와 일반 logistic Elo도 계속 구별한다. [^R53]

H 경로의 작은 CPU 평가기는 전체 CPU core·RAM 한도 안에 들어간다. LC0에도 같은 CPU/GPU 한도를 제공하고 각자 validation 세트에서 정상적인 옵션 튜닝을 허용한다. 사용한 CPU량이 다르더라도 동일 자원 상한 비교의 의미를 명시하며, 전력·비용 동일 조건 비교가 필요하면 별도 실험군으로 둔다.

고정된 신경망의 온라인 가중치 변경은 주 평가에서 금지한다. 반면 F06/F07 같은 **게임 안의 search history·correction table 갱신은 명시적으로 허용하는 옵션**으로 둔다. 이는 원래 2.3절의 ‘온라인 가중치 갱신 금지’와 다르다. 자기 생각 시간에만 갱신하고 `ucinewgame`에서 초기화하며, 원시 평가 cache를 오염시키지 않는다. 영구적인 상대 학습·다른 게임 결과 유입은 별도 프로토콜 없이는 금지한다.

CPU helper나 speculative 요청도 상대 차례에 계산하지 않는다. 늦게 끝난 이전 요청은 generation/deadline 검사를 거쳐 버리고, 실제 착수 이후의 계산이 다음 시계에 몰래 이득을 주지 않도록 중단·격리 정책을 둔다. 큰 GPU 작업의 취소 불가 구간과 잔여 실행도 계측한다.

최종 로그에는 `track=G/H/C`, helper 모델·호출 횟수·사용 시간, raw/corrected value 구분, cache provenance, CPU/GPU 실제 사용량, board 입력/모델/검색/시계 manifest를 추가한다. 같은 net의 speedup, 새 모델의 strength gain, 시간 관리의 gain을 하나의 원인으로 묶지 않는다.
